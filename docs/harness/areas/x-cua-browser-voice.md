## 1. Purpose

Area A16 defines two **seams** with no provider behind them: one fixed set of browser tools and one fixed set of desktop tools, each with a Go interface that some backend must implement. This area supplies the backends. For **computer use** (driving desktop applications) the owner decided that the Go project ships no native code, so the only backend is an adapter in front of a desktop-control server the operator installs ([DH-ADR-19](../design.md#dh-adr-19)). For **browser use** the project ships one backend that needs nothing but an installed Chrome, and admits two optional ones that need Node.

It also covers **voice input**: a microphone control in the message composer that turns speech into text in the unsent draft. Nothing here gives the model a new tool, and dictation never sends a message. Without this area the browser and computer tools of A16 would always answer `unavailable`, and five upstream packages for dictation would have no counterpart.

## 2. Vocabulary

Terms defined by A16 are used as written: **provider slot**, **launch mode** and **attach mode**, **page description**, **element reference**, **provider profile**, **application grant**, **desktop lease** ([document-browser-computer.md §2](document-browser-computer.md#2-vocabulary)). **Island**, **fragment** and **region** are C1's ([ui-core.md](ui-core.md)).

| Term | What it is | Why it exists |
|---|---|---|
| **Adapter** | Harness code that implements a seam's Go interface by calling the tools of an MCP (Model Context Protocol) server. | The model's tools are fixed by A16; a server's own tool names never reach the model. |
| **Recipe** | The part of an adapter that is specific to one server: its default command, the version it was tested with, and how each interface method maps to one of the server's tools. | A new server is a new recipe, not a new adapter. |
| **Cua Driver** | A third-party desktop-automation program (`cua-driver`) from the `trycua` project that offers its operations as an MCP server. | The one computer-use server this design carries a recipe for. |
| **Daemon** | A long-lived background program. On macOS `cua-driver mcp` forwards to a separate `CuaDriver.app` daemon unless started with `--direct` (`packages/experimental/computer-use-cua-driver-mcp/README.md:69`). | The operating system ties desktop permissions to that application's identity; the harness never owns it. |
| **CDP** | Chrome DevTools Protocol: the control protocol of Chromium-family browsers. | The shipped browser provider speaks it directly, with no Node and no driver process. |
| **Recognition provider, processing location** | A provider is a named backend that turns one complete recording into text. Its location is `host-local` (the recording stays on the machine that runs `dsh`) or `cloud` (it is sent to a service). | Where speech is processed is the user's explicit choice, shown before recording; a local failure must never upload speech. |
| **Canonical recording** | A WAV file: one channel, 16,000 samples per second, 16-bit samples. | One format that the browser produces and every provider accepts. |

### 3.2 Behaviour

**Computer use.** A shared service only records which one provider is mounted (`docs/subsystems/computer-use.md:37`). Upstream has four providers (`:30-35`). Two are first-party: a Swift helper and a .NET helper, each a separate signed or locally built program, reached through the shared `cua` library. That library gives the model retained application and window objects, asks the user for consent per application before any launch, observation or input, and stores "always allow" grants and per-conversation decisions in profile storage (`cua/README.md:50`, `:92`). The model reaches the objects through a program: agents on the programmatic preset get a raw `cua` binding, every other agent gets `cua_run_code`, a TypeScript runtime with one retained Node process per agent (`cua/README.md:34`, `:108-110`). The other two providers wrap **Cua Driver**. The MCP form starts an installed `cua-driver` with the argument `mcp` and registers whatever tools it lists under their own names; installation and permissions stay with the driver (`computer-use-cua-driver-mcp/README.md:28`, `:38-45`, `:55`). The native form loads the driver into the host from npm, so a native crash ends the host and the desktop permission is that of whatever launched the harness (`computer-use-cua-driver-native/README.md:43`). Neither Cua Driver provider asks for consent per application or serialises sessions: "callers coordinate" (`docs/subsystems/computer-use.md:43`). A fifth package turns the first-party stack around and serves it to other harnesses as an MCP server, granting consent unattended or forwarding it to the client (`cua-mcp/README.md:12`).

**Browser use.** The same name-only service exists for browsers (`docs/subsystems/browser-use.md:17`). The runtime library keeps one browser per live session, runs that session's calls in order, reserves an attached browser for one session, and for MCP providers starts one server per agent inside the `agent/created` event, so a server that cannot start rejects session creation (`browser-use-runtime/README.md:30-36`). The Playwright and Chrome DevTools providers start a pinned npm package under the host's own Node executable and pass its tools through under `mcp__<server>__` names (`browser-use-playwright-mcp/README.md:60`, `:84`). The Stagehand provider starts Chromium itself with a debugging port and a private profile, and answers `act`, `observe` and `extract` with a second model whose key is forwarded to a browser extension and whose requests are not captured (`browser-use-stagehand-native/README.md:45`, `:61`, `:94`).

**Voice input.** The browser owns the microphone and the unsent draft; the host owns recognition (`docs/subsystems/voice-input.md:15`). A click starts recording and shows levels; Stop converts the capture to a canonical recording in the browser, sends it to the host as base64, and inserts the returned text as one undoable edit, but only if the draft has not changed since recording began; otherwise the text is kept beside the microphone for explicit insertion (`:17`, `:27`; `client-ui-voice-input/README.md:46`). The host resolves exactly one provider by id; "audio never falls back to a different provider" (`docs/subsystems/voice-input.md:9`). The one provider runs SenseVoice with a voice-activity detector in a managed subprocess, with a bounded queue, a deadline and an idle release; the native runtime is installed with the product, and about 239 MB of model files are downloaded on an explicit "Download and prepare", verified against pinned sizes and SHA-256 values, or supplied as existing paths for offline deployments (`speech-to-text-sensevoice/README.md:28-36`, `:46`, `:74`). Limits are 4 MiB and 120 seconds per recording (`api-speech-to-text/src/index.ts:31-32`). Recognition writes no session event and starts no turn (`.agents/notes/implemented/architecture/2026-09-16-experimental-voice-input.md:17`). Upstream rejected recognition in the browser because it "does not provide a uniform local-processing guarantee" (same note, `:25`).

**Events, persistence, config.** The area defines no event and no session event type. It persists application grants (`$DSH_HOME/storages/cua_permissions_<sha256>.json`, `cua/README.md:92`) and model caches. Ten config schemas and four services are listed in [§6.2](#62-contracts).

### 3.3 Failure, retry, rollback and cleanup upstream

No provider can undo input that reached a page or a desktop, and all say so (`computer-use-cua-driver-native/README.md:135`; `browser-use-runtime/README.md:86`). A Cua Driver start-up failure releases the registration; a failed native shutdown keeps it until the host restarts (`computer-use-cua-driver-native/README.md:136`). A browser whose close fails keeps its reservation, and with Stagehand the user is told to restart the host (`browser-use-stagehand-native/README.md:159`). A speech recognition error discards the worker; a cancelled recording never runs; verified model files survive a failed or cancelled download and a partial file starts again (`speech-to-text-sensevoice/README.md:34`, `:46`). **Left behind or uncertain:** delivered input; a helper or browser process whose close failed; consent records of deleted conversations, which are never removed (`cua/README.md:161`).

## 6. Go design

### 6.1 Shape

Packages sit under `src/harness/internal/x` ([../design.md §4.2](../design.md#42-go-module-layout)). Every component is a default-off entry of the experimental bundle. A provider imports its seam's contract package and never the tools package; A16's import-direction test covers them.

| Package | Component (config row) | Provides | Injects | Why it exists |
|---|---|---|---|---|
| `computermcp` | `x.computer.mcp` | Registers one `computer.Provider` | `computer.Key` (A16), `mcp.Key` (A15) | The only route to computer use: the adapter, and the recipe `cua-driver` |
| `browsercdp`, with the library `browsercdp/launch` (`Find`, `Start`, `Stop`, `Sweep`) | `x.browser.cdp` | Registers the `browser.Provider` named `cdp` | `browser.Key` (A16), `subprocess.HostKey` (A09), policy resolver (A10) | The provider the binary ships and the only importer of `chromedp`. `launch` is what is left of upstream's runtime package: finding a browser, its private profile, its life and death |
| `browsermcp` | `x.browser.mcp` | Registers a `browser.Provider` named after its recipe | `browser.Key`, `mcp.Key`, `web/guard` (A15) | Optional: `playwright` and `chrome-devtools` recipes for operators who have Node |
| `speech` (contract) and `speech/core` | `x.speech` | `speech.Key` with `speech.Service`; `Provider`, `Info`, `Transcript`; error codes; `speech.StatusChanged`; three routes | `web.Routes` (A19), the layer editor (A21) | What the routes, the island and providers share; selection by exact id, limits, validation of the recording |
| `speech/command` | `x.speech.command` | One `host-local` provider | `speech.Key`, `subprocess.HostKey`, policy resolver | Runs the operator's recognition program on one file |
| `speech/remote` | `x.speech.remote` | One `cloud` provider | `speech.Key`, `egress` (A23), credentials (A17), the sharing gate (A18) | Explicit, labelled, never a fallback |
| `voiceinput` | `x.voice-input` | Nothing; contributes to `composer.controls`, registers the island `dsh-voice` | `shell` (C1), `speech.Key`, the message catalogue | The microphone control |

```go
package speech
type Service interface {
    Register(owner *cordis.Context, p Provider) error               // exact id; a duplicate fails; an effect of owner
    Catalog() Catalog                                               // every provider's Info and Status, the selection, the limits
    Transcribe(ctx context.Context, r Request) (Transcript, error)  // Request{Provider, Language, WAV}; exactly one provider, never another
    Select(ctx context.Context, s Selection) error                  // owner only; writes defaultProvider and language to the writable layer
}
type Provider interface { Info() Info; Status() Status; Transcribe(ctx context.Context, wav []byte, language string) (Transcript, error) }
type Info struct { ID, Name string; Location Location; Languages []string; Endpoint string } // Location: HostLocal | Cloud. Transcript{Text, AudioSeconds, RecognitionSeconds}
```

`computer.Provider`, `browser.Provider`, `browser.Browser` and `mcp.Handle` are used exactly as A16 and A15 define them.

**How the computer-use adapter works.** At load it registers itself in the provider slot, then registers one MCP entry with A15: `transport: stdio`, the configured `command` and `args`, `scope: host`, `expose: none`, and `allowTools` set to the recipe's short list. One driver process serves the host, because there is one desktop and A16's lease lets one session act at a time. When the entry connects, the adapter reads `Handle.Tools()` and checks that every tool the recipe needs exists with the arguments it sends; a mismatch leaves the provider `unavailable` with a reason that names the missing tool and the driver's version. It records the version the driver reports and warns if it differs from the recipe's tested version. If the recipe names a permission-status tool it is called once without prompting and the answer becomes a line of `computer.Status`. Each `computer.Provider` method is then one `Handle.Call`:

| `computer.Provider` method | Driver tool | Arguments sent | What comes back |
|---|---|---|---|
| `Apps` | `list_apps` | none | Rows marked running become `App{ID: pid, Name, Identity}`; `Identity` is the row's stable identifier where there is one, otherwise the process id |
| `Windows(app)` | `list_windows` | `pid` | `Window{ID: window_id, Title}` |
| `Snapshot(w)` | `get_window_state` | `pid`, `window_id`, `include_screenshot: false`, `max_elements`, `max_depth` | The tree; each actionable element's `element_token` is its reference; `truncated` and `degraded` are passed on |
| `Screenshot(w)` | `get_window_state` | the same window, tree off, `max_image_dimension` | One image of that window, already an attachment (A15) |
| `Click`, `Type`, `Key`, `Scroll` | `click`; `type_text`; `press_key` or `hotkey`; `scroll` | the window; an `element_token` or a point in the window's screenshot; the text, key or chord; a `direction` from the sign of `dx` and `dy`; always `delivery_mode: background` | "delivered", with the driver's `verified` and `effect` fields as text. `Close` calls nothing: the entry's fiber stops the process |

Tool names are from the driver reference; `pid`, `window_id`, `get_window_state`, `click` and `check_permissions` also appear in upstream's own fixtures and guidance (`packages/experimental/computer-use-cua-driver-native/tests/fixtures/cua-driver.ts:12-25`; `…/README.md:97`). The adapter never calls the driver's other tools, among them whole-display capture (`get_desktop_state`), `launch_app`, `kill_app`, `run_script`, the clipboard and browser tools, `set_config`, `check_for_update` and `install_extension`: they are outside `allowTools` and outside the recipe. It never sends `delivery_mode: foreground`, so the harness does not take the user's foreground or pointer; when background delivery does not land, the result says so and the model asks the user to bring the window forward. A point is scaled by the ratio of the image the driver produced to the image stored for the model, and `max_image_dimension` is set from the attachment limits so that the ratio is normally one.

**Does Cua Driver fit A16's provider profile?** A16 left this open because the tool list is not in the upstream checkout. Read against the driver reference and upstream's fixtures:

| Profile item ([A16 §6.2](document-browser-computer.md#62-contracts)) | Evidence | Verdict |
|---|---|---|
| 1. A stdio MCP program that reports name and version | `cua-driver mcp` (`computer-use-cua-driver-mcp/README.md:38-45`). Whether the handshake carries the program version is not documented | Fits; the version is open |
| 2. Lists applications with a stable identity | `list_apps` lists running and installed applications; `name`, `running` and `pid` are shown. A bundle identifier or path field is not confirmed | Fits; a grant falls back to the process id and then ends when the application exits |
| 3. Lists one application's windows | `list_windows` takes `pid` and returns `window_id` and `title`; size is not confirmed | Fits |
| 4. Observation by window | `get_window_state` returns the accessibility tree with an `element_token` per element and a screenshot of that window | Fits |
| 5. Input by window and reference or point | `click`, `type_text`, `press_key`, `hotkey` and `scroll` address a `pid` and window and take a token or window-local screenshot pixels | Fits; how far one `scroll` moves is open |
| 6. Reports delivery, errors plainly, opens no system prompt | Results carry `verified` and `effect`; upstream's guidance says a delivered click proves no outcome (`…cua-driver-native/README.md:99`); `check_permissions` is called with `prompt: false` (`…cua-driver-mcp/README.md:69`). The error shape for a stale token or a vanished window is not documented | Fits; the error mapping is open |
| 7. Honours cancellation and exits when its input closes | Not documented. On macOS the default `mcp` mode is a proxy to a daemon that keeps running | Open for the child; the daemon is a shared resource the harness does not own |
| 8. Needs no sampling, elicitation or special method | Nothing in the reference requires one, and A15's client advertises no capability | Fits |

**Answer: yes in shape, with `Targeting: window`.** Items 2, 6 and 7 and the version need one run against the real program ([DH-E-XCUA-1](#dh-e-xcua-1)); until that run is recorded the recipe is unproven. Upstream's own `cua-mcp` server would *not* fit: its only action tool takes a program, and its consent arrives by elicitation.

**What an operator installs and configures for computer use.** (1) Cua Driver, at the version the recipe names (upstream pinned 0.28.0). (2) The operating-system permissions it asks for, granted by hand to the driver's own application; on macOS Accessibility and Screen Recording. (3) A logged-in, unlocked graphical session. (4) Three entries in a configuration layer: A16's `computer` and `computer.tools`, and `x.computer.mcp` with `command` if `cua-driver` is not on `PATH`. (5) If the driver cannot start under the default confinement, `confinement.mode: danger-full-access` on that entry, which the status then reports. `dsh doctor` (A24) and the status view show the provider, its version, its targeting and the permission line. Steps 1 to 3 are restated from [../libs/cua-helper.md](../libs/cua-helper.md) §6.

**The shipped browser provider, `cdp`.** `launch.Find` returns the configured `path`, else the first existing well-known location of stable Chrome for the operating system; none is `browser/unavailable` naming Chrome, and nothing is downloaded. `launch.Start` creates an owner-only profile directory under the process's run directory in the harness home and starts the browser through `subprocess.HostKey` with an explicitly built environment and a fixed flag list: `--remote-debugging-pipe`, the profile path, no first-run or default-browser prompts, headless unless configured otherwise, and never a debugging port. The provider implements chromedp's `Allocator` so that chromedp drives the pipe and never starts a process itself ([../libs/browserbasehqstagehand.md](../libs/browserbasehqstagehand.md) §6). `Open` in attach mode connects to A16's configured endpoint instead. The methods of `browser.Browser` map to CDP domains: tabs to `target`; `Navigate` and `Page` to `page`; `Snapshot` to the `accessibility` tree, filtered to named and actionable nodes up to the limit in `SnapshotOptions`, each with a reference minted for that snapshot; `Screenshot` to `page`; `Click`, `Type`, `PressKey` and `Scroll` to `input` after resolving a reference to a point through `dom`; `WaitFor` to a bounded poll. `Page.HasCredentialField` is true when the page has a password or one-time-code input. The **guard** A16 hands over at `Open` is called for every top-level document request, redirects included, by pausing such requests through the `fetch` domain; a refused request is failed in the browser. Downloads are denied through the `browser` domain. `launch.Stop` closes the transport, runs the stop ladder of [execution.md](execution.md), confirms the exit and removes the profile; it is safe to call twice. `launch.Sweep` runs at component start and removes profile directories under run directories whose kernel lock is free.

**The optional Node providers.** One adapter, two recipes. Per session it registers an MCP entry (`scope: agent`, `expose: none`) whose arguments the recipe builds from config, exactly as [../libs/playwrightmcp.md](../libs/playwrightmcp.md) (R1, R2) and [../libs/chrome-devtools-mcp.md](../libs/chrome-devtools-mcp.md) (R1, R2) state, and maps each `browser.Browser` method to one server tool. The server, not the harness, starts the browser, so the adapter cannot pause a request. It meets the guard another way: the browser is pointed at a loopback forward proxy that the adapter owns for that session and that asks the guard about every connection. A recipe ships only if its server has such an option and the provider passes A16's `browsertest`; attach mode is not offered through these recipes.

**Speech.** `Transcribe` checks the byte limit, validates the canonical recording and its duration, resolves the named or default provider and the language, and calls that provider. The **command provider** keeps a bounded queue and runs one recording at a time: it writes the bytes to an owner-only file in its run directory, starts the configured program with the `{wav}` and `{language}` placeholders filled, under a read-only policy with that directory as the only write root and the network denied, reads bounded output as the transcript, and removes the file before it returns. `confinement` has the meaning A16 gives it for the office engine: where a backend cannot deny the network (Windows), `required` runs with what the backend governs and the settings fragment says so. The **remote provider** posts the recording as a multipart form to a configured transcription endpoint through `egress`, and only while it holds a permit from A18's sharing gate.

**Voice input in the composer.** The component contributes one control to C3's `composer.controls` region. With no usable selected provider the control is a link to the speech settings fragment. Otherwise it is the island `<dsh-voice>`, unframed, with limits, addresses and translated labels as attributes. A click asks the browser for the microphone, records with a level display, and offers Cancel and Stop; Escape or hiding the page discards. Stop resamples to the canonical recording in the browser and posts it. The answer is a fragment holding the text. If the composer's draft revision still equals the one captured when recording began, the island dispatches a DOM event that inserts the text at the caret as one undo step; otherwise the fragment keeps the text with Insert and Discard buttons. The chosen input device is remembered in the browser's own storage, because device identifiers belong to one browser.

### 6.3 Ownership, failure, retry, rollback and cleanup

| Resource | Class | Owner (releases it) | Who merely has access |
|---|---|---|---|
| The installed driver, its daemon, its permissions; installed Chrome; Node and an MCP browser server; the recognition program and its model files | shared | The operator. The harness never installs, updates, stops or removes them | The harness may start the program |
| The `cua-driver mcp` child | created | The MCP entry's fiber under `x.computer.mcp` | Every session, one at a time under A16's lease |
| A launched browser, its pipe and profile directory; a per-session MCP server and its guard proxy | created | A16's browser service, for one session, through `Browser.Close` | That session's agents |
| A recognition child and its temporary recording file | created | The transcription call | n/a |
| The microphone stream and the unsent recording | created | The island; released on Stop, Cancel, page hide or removal of the element | n/a |

| Situation | What happens | Undone, and what stays uncertain |
|---|---|---|
| The driver program is missing, or lacks a tool the recipe needs | `computer/unavailable` naming the program or the tool; no process stays; the slot remains registered so that fixing the configuration needs no restart | Nothing ran |
| The driver crashes or hangs | Pending calls fail as `computer/lost`; A15 restarts it under its budget; nothing is replayed | **Uncertain:** what the driver did; the daemon may still run |
| `x.computer.mcp` unloads | The entry is stopped and confirmed first, then the slot is released. An unconfirmed stop keeps the slot | **Uncertain:** a surviving process is named in the status |
| Chrome is not found, or does not start in time | `browser/unavailable` naming what to install; the tree is stopped and the profile removed before the error returns | Nothing is reserved |
| The browser dies, or the host is killed | Pending calls fail as `browser/lost`. A later start sweeps orphaned profiles | **Uncertain:** whether a browser outlives a killed host on each system ([DH-E-XCUA-2](#dh-e-xcua-2)) |
| A browser or desktop call is cancelled | The result says the outcome is unknown and tells the model to observe first | Delivered input stays delivered |
| The recognition program is missing, fails, prints nothing usable or exceeds `timeout`; the remote endpoint fails, or the sharing gate is closed | `speech/unavailable`, `speech/failed` or `speech/timeout`, or `speech/sharing-off` before any request; the tree is stopped; the file is removed; nothing is retried and no other provider is tried | The recording is gone; the user records again. **Uncertain:** whether a remote request that failed in flight was received |
| The draft changed, the session was switched, or the microphone was refused or lost | The text is offered for explicit insertion, or discarded on a session switch; a microphone failure shows the browser's reason and offers a retry | Nothing was inserted or sent |

## 7. Decisions

<a id="dh-adr-xcua-1"></a>
### DH-ADR-XCUA-1 Computer use is one adapter with a Cua Driver recipe behind an unexposed MCP connection; upstream's first-party stack is not ported
- **Decision.** (a) The five first-party packages (`cua`, `cua-macos`, `cua-windows`, `cua-bundle`, `cua-mcp`) are dropped, and the in-process Cua Driver provider is merged into the external one. (b) `x.computer.mcp` implements A16's `computer.Provider` over `mcp.Handle`, with `expose: none` and an `allowTools` list. (c) A recipe is compiled-in Go: data plus small mapping functions. One recipe exists, `cua-driver`, registered with `Targeting: window`. (d) The adapter checks the server's tool list at start-up and is `unavailable` on a mismatch. (e) It always asks for background delivery and scales points itself. (f) The harness serves computer use to no other program.
- **Why.** (a) is [DH-ADR-19](../design.md#dh-adr-19). (b) and (d) keep A16's promise that a provider change never changes the model's tools, and turn upstream's "driver upgrades can change the discovered catalog" from a silent change into a visible refusal. The allow-list keeps the rest of the driver's tools (the driver reference lists 66 in all), such as whole-screen capture, script execution and killing a process, out of reach of the model. (e) keeps two upstream rules: do not disturb the user's pointer, and do not make the model do scaling arithmetic.
- **Tradeoff.** Exactly one server is supported until someone writes a second recipe; a server cannot be mapped from configuration alone. Hover, drag, held keys, launching an application and foreground delivery are unavailable. An application's identity is what the driver reports. The mapping can break with any driver release, and the project neither pins nor audits the driver. Scope boundary of this record: the evidence proves the computer-use contract (the action mapping, the approval path, the results and the cleanup) with a replayed model on one test application, and does not measure whether a real model completes real desktop tasks, because task success is a property of the chosen model and of a driver and applications the project neither ships nor pins, so a success rate measured here would not hold for the operator's installation.
- **Serves.** [DH-O-10](../design.md#dh-o-10), [DH-O-7](../design.md#dh-o-7). **Verified by.** `DH-T-XCUA-1`, `DH-T-XCUA-2`, `DH-T-XCUA-3`, [DH-E-XCUA-1](#dh-e-xcua-1).

<a id="dh-adr-xcua-2"></a>
### DH-ADR-XCUA-2 The shipped browser provider is `cdp`: chromedp over a pipe to an installed Chrome that the harness starts and owns
- **Decision.** As [§6.1](#61-shape). Module `github.com/chromedp/chromedp` v0.24.0 with `github.com/chromedp/cdproto`, as recorded by `DH-LIB-STAGEHAND` and `DH-LIB-CDPROTO` in [../libs/browserbasehqstagehand.md](../libs/browserbasehqstagehand.md) (re-checked on 2026-11-18 with `go list -m -json`). The Stagehand provider is dropped whole. Upstream's runtime package is not a package of its own: session ownership is A16's service, and what remains is `browsercdp/launch`.
- **Why.** It is the one option that needs neither Node nor a second model ([DH-ADR-STAGEHAND-2](../libs/browserbasehqstagehand.md#dh-adr-stagehand-2), [DH-ADR-24](../design.md#dh-adr-24)). Because the harness starts the browser, it can keep every rule of [DH-ADR-MEDIA-5](document-browser-computer.md#dh-adr-media-5): a private profile, no listening port, the guard on every document request.
- **Tradeoff.** Chromium family only. The harness owns a page-description format built from the accessibility tree. Stable Chrome is the only browser looked for until a scenario proves Edge and Chromium. The pipe transport with a browser started outside chromedp is unproven on Windows ([../libs/browserbasehqstagehand.md](../libs/browserbasehqstagehand.md), risk 2). A browser cannot run inside the file sandbox, so it is started unconfined and reported so.
- **Serves.** [DH-O-10](../design.md#dh-o-10), [DH-O-4](../design.md#dh-o-4), [DH-O-7](../design.md#dh-o-7), [DH-O-14](../design.md#dh-o-14). **Verified by.** `DH-T-XCUA-4`, `DH-T-XCUA-5`, [DH-E-XCUA-2](#dh-e-xcua-2).

<a id="dh-adr-xcua-3"></a>
### DH-ADR-XCUA-3 The two Node browser servers are optional recipes that must pass the same conformance suite, or they do not ship
- **Decision.** Playwright MCP and Chrome DevTools MCP are reached through one adapter with a recipe each. The operator installs Node and the server ([DH-ADR-PLAYWRIGHTMCP-1](../libs/playwrightmcp.md#dh-adr-playwrightmcp-1)). A recipe is accepted only when the provider passes A16's `browsertest`, including the navigation guard, which the adapter enforces through a per-session loopback proxy. Launch mode only.
- **Why.** [DH-O-10](../design.md#dh-o-10) is only shown to hold for browser use when two real providers produce the same tool schema. Under a fixed catalogue these servers add nothing the model can see, so they may not cost the seam a security rule either.
- **Tradeoff.** The last deliverable to build and the first to cut. Whether each server accepts a proxy setting, and what its tools are called, is not in the upstream checkout and must be read from the installed server. The server's profile and transport are its own.
- **Serves.** [DH-O-10](../design.md#dh-o-10), [DH-O-7](../design.md#dh-o-7). **Verified by.** `DH-T-XCUA-6`, [DH-E-XCUA-3](#dh-e-xcua-3).

<a id="dh-adr-xcua-4"></a>
### DH-ADR-XCUA-4 Speech is recognised on the host by a program the operator installs; providers are explicit and never fall back
- **Decision.** Of the three options, the Go design takes the second: the host runs an operator-installed recognition program as a child process. The harness ships no recogniser and downloads neither a runtime nor a model. Any program that reads one WAV file and prints text fits the command contract; the documented example is the prebuilt sherpa-onnx runtime with SenseVoice. Providers register under exact ids with a processing location; a failed provider is never replaced by another. A cloud provider exists only if the operator configures one, and it sends only under A18's sharing gate, with a permit of kind `speech-audio`. Speech is off in a fresh home: no provider is selected, and the composer shows a link to the settings instead of a microphone. Recommended default, not confirmed by the owner: a cloud speech endpoint counts as a sender, so the one off-switch stops it ([DH-ADR-27](../design.md#dh-adr-27) leaves a sender under the switch even when the user configured it; dictation to a local recogniser is unaffected), and no command of the harness fetches a recogniser or a model ([§10](#10-open-questions-and-limitations)).
- **Why.** Recognition in the browser gives no guarantee about where audio goes, which upstream already found and [DH-ADR-9](../design.md#dh-adr-9) makes disqualifying. Dropping the feature loses dictation for users who cannot type comfortably. A child process keeps the binary pure Go ([DH-ADR-15](../design.md#dh-adr-15)). Not downloading follows the rule the design applies to LibreOffice, Chrome and the driver. It also sidesteps the open question in [../libs/sherpa-onnx-node.md](../libs/sherpa-onnx-node.md) about that runtime's command line: the flags are configuration, not code.
- **Tradeoff.** No one-button set-up: the operator downloads a runtime and about 239 MB of model files by hand. This departs from that library specification, which proposed a pinned download; its requirement R3 and test `DH-T-SHERPAONNX-3` have nothing to apply to here. A program started per recording loads its model each time; the delay is unmeasured. Upstream's repair of late speech onset is not available.
- **Serves.** [DH-O-14](../design.md#dh-o-14), [DH-O-10](../design.md#dh-o-10), [DH-O-7](../design.md#dh-o-7). **Verified by.** `DH-T-XCUA-7`, `DH-T-XCUA-8`, `DH-T-XCUA-9`, [DH-E-XCUA-4](#dh-e-xcua-4).

<a id="dh-adr-xcua-5"></a>
### DH-ADR-XCUA-5 Voice input is an unframed island that only ever proposes text for the draft
- **Decision.** As [§6.1](#61-shape). The island records, converts and posts; the host answers a fragment; insertion happens only into an unchanged draft or on an explicit click. There is no automatic send, no always-on microphone and no streaming. Scope boundary of this record: dictation takes one complete recording and returns text, with no audio file upload and no stored history of transcripts, because a history would keep speech the user never chose to send, and an uploaded file is an attachment, not dictation.
- **Why.** A microphone needs code in the browser between two requests, which is C1's rule for allowing an island ([DH-ADR-GOUISTACK-6](../libs/go-ui-stack.md#dh-adr-gouistack-6)). Keeping the transcript out of the log until the user submits ordinary text preserves [DH-O-4](../design.md#dh-o-4) with no new event.
- **Tradeoff.** No dictation with scripts off. Inference from the web platform, not from upstream: browsers give the microphone (`getUserMedia`) only to a secure context, which loopback and HTTPS are and plain HTTP on a network address is not, so a host reached that way cannot record; the same rule is why [libs/go-ui-stack.md](../libs/go-ui-stack.md) (`DH-ADR-GOUISTACK-9`) needs TLS for notifications from another machine. The recording is held in browser memory until Stop.
- **Serves.** [DH-O-12](../design.md#dh-o-12), [DH-O-4](../design.md#dh-o-4). **Verified by.** `DH-T-XCUA-10`, [DH-E-XCUA-4](#dh-e-xcua-4).

### 9.2 Real-environment scenarios

<a id="dh-e-xcua-1"></a>
#### DH-E-XCUA-1 The recipe against a real Cua Driver on a logged-in desktop
- **Proves.** DH-D-XCUA-1. A16's [DH-E-MEDIA-5](document-browser-computer.md#dh-e-media-5) proves grants and the lease on the same set-up; this one proves the mapping and settles the open profile items.
- **Given.** A macOS and a Windows machine, each with a logged-in, unlocked graphical session; Cua Driver installed by its own instructions, its version noted, permissions granted by hand; the built `dsh`; a small test application with one button, one text field and a scrolling list; the replay model provider; an owner answerer that grants the test application for the session.
- **When.** Start with `command` pointing nowhere. Then start normally and record the handshake; list applications and windows; take a snapshot and a screenshot; click the button by reference and by point; type; press a chord; scroll; reuse a token from the earlier snapshot; cancel a call mid-flight; close the test application and act on its window; stop the host and list processes.
- **Then.** The first start reports `computer/unavailable` and starts nothing. The recorded handshake shows whether a version is reported; the listing shows whether a stable identity field exists. The application records the click, the text, the chord and a scroll in the right direction. The old token and the vanished window give errors that map to A16's codes. The cancelled call returns within the bound. No whole-screen image exists in the session's attachments, and the user's pointer and foreground window did not change. After the stop, no child of `dsh` remains; a daemon that remains is listed in the report as the driver's own.
- **Cleanup.** Close the test application; remove the temporary home. The driver, its daemon and its permissions are left alone. On failure keep the driver's output and the process list.

<a id="dh-e-xcua-2"></a>
#### DH-E-XCUA-2 `cdp` on real Chrome: a pipe, a private profile, the guard, and no survivor
- **Proves.** DH-D-XCUA-2. It runs beside A16's [DH-E-MEDIA-4](document-browser-computer.md#dh-e-media-4) and adopts the scenario handed over by [../libs/browserbasehqstagehand.md](../libs/browserbasehqstagehand.md) §8.
- **Given.** Linux, macOS and Windows runners with stable Chrome; the built `dsh` with `x.browser.cdp` enabled; a test server on an allowed loopback address with a page, a form, and a link that redirects to a link-local address; the replay model provider.
- **When.** A session navigates, takes a snapshot, clicks by reference, types, and takes a screenshot; follows the redirecting link; the host is killed while the browser is open; a new host starts on the same home. Repeat once with Edge.
- **Then.** The server saw the click and the text. While the browser ran, its process had no listening TCP port. The redirect was refused with `browser/navigation-refused` and the server saw no request at the redirect target. After the kill, the report states for each operating system whether the browser exited by itself; after the new start no orphaned profile remains. The Edge run is recorded as pass or fail and decides whether Edge joins the discovery list.
- **Cleanup.** Stop the server; remove the home. If a browser survives, fail and keep the process list and profile path.

<a id="dh-e-xcua-3"></a>
#### DH-E-XCUA-3 A real Node browser server behind the same tools
- **Proves.** DH-D-XCUA-3.
- **Given.** A runner with Node, Playwright MCP installed by the operator's own command, and Chrome; the fixtures of [DH-E-XCUA-2](#dh-e-xcua-2); the request headers recorded from that scenario.

<a id="dh-e-xcua-4"></a>
#### DH-E-XCUA-4 Dictation with a real browser and a real recognition program, with nothing leaving the machine
- **Proves.** DH-D-XCUA-4, DH-D-XCUA-5.

## 10. Open questions and limitations

**Needed from other areas** (requests, not their interfaces).

1. **A16.** (a) `computer.Provider.Snapshot` takes no options: a per-call node or depth limit, which upstream had, needs an argument in the catalogue. (b) The size at which a screenshot is stored for the model must be readable by a provider, so that a point can be scaled. (c) [DH-E-MEDIA-5](document-browser-computer.md#dh-e-media-5) expects that "no server process remains"; on macOS the driver's daemon may. (d) `browser.Info` needs a way to say that a provider's browser was started by a third party.
2. **A15.** Confirmation that `allowTools` also limits `Handle.Call`, and that one entry may be registered by a provider per session. A15 asks this area for the tool set of an MCP serving command: there is none, by [DH-ADR-XCUA-1](#dh-adr-xcua-1) (f).
3. **A17.** The `application` scope's application id is the driver-reported identity or, failing that, a process id: confirm that a process id is acceptable as a grant's name.
4. **A19.** The three routes are registered by this area through `web.Routes`; nothing more is needed of [api.md](api.md).

**Settled with A19, C1, C3, A18 and A10.** `web` writes a `Permissions-Policy` that denies every feature, and the voice-input component registers the allowance `microphone=(self)` with `web.Routes.AllowFeature`, an effect ([api.md §6.1](api.md#61-shape)). `speech-audio` is a kind of A18's sharing gate. The recognition program and the session's browser get their policy from `Resolver.ForHelper` (the browser as a registered helper kind with the reported `Unconfined` flag); both are untrusted trees. Text reaches the composer by the `dsh:insert-text` event ([ui-chat.md §6.1](ui-chat.md#61-shape)), which keeps the caret; with the composer island not loaded the control appends through `Drafts.Prefill`.

**Recommended default, not confirmed by the owner.** (a) A cloud speech endpoint the user configured is a sender under the one off-switch ([DH-ADR-27](../design.md#dh-adr-27)). (b) No `dsh` command fetches a pinned recogniser and model: it would restore upstream's one-button set-up and would download executable code.

**Library documents now agree.** [../libs/trycuacua-driver.md](../libs/trycuacua-driver.md) follows A16 (fixed catalogue, application grants), and [../libs/sherpa-onnx-node.md](../libs/sherpa-onnx-node.md) has an operator-installed program and no download; its test `DH-T-SHERPAONNX-3` ("no request is made; a missing program reports `unavailable`") is part of the proof of [DH-D-XCUA-4](#dh-d-xcua-4).

**Open, to be settled by scenario.** Every profile item marked open in [§6.1](#61-shape); whether the driver starts under the default confinement; whether the pipe transport works on Windows; whether a browser outlives a killed host; the Node servers' tool names and proxy options; the recogniser's command line and its per-recording start time.

**Limitations kept.** One supported desktop driver, whose code and updates the project does not control. No hover, drag, held keys, application launch or foreground delivery. Chromium-family browsers only. The 32 carried units of [§5](#5-tech-debt-and-its-resolution). Dictation needs scripts, a secure context and an operator-installed recogniser, and handles complete recordings only.

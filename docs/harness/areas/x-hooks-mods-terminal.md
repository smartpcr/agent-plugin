## 1. Purpose

This area holds seven experiments that connect the harness to other products and ways of working. **Hooks** let a person's existing Claude Code or Codex hook scripts run at fixed moments of an agent's work and veto or annotate what happens. **Claude Code mods** ran a second kind of Claude Code extension, a JavaScript module whose `register` function installs handlers (`x/claude-code-mods/README.md:28`), inside the host. **Auto review** replaces a person's approval with a model's judgement of each tool call. **Webhooks** start a session when an outside service, such as GitHub, reports an event. The **ralph loop** runs a task as a sequence of fresh agents. The **OAR provider** delegates a task to another vendor's coding agent through the OAR adapter library. The **terminal tools** give the model terminals that a person can watch and take over.

Without this area a user loses nothing a first product needs, but cannot reuse existing hook scripts, cannot react to repository events unattended, and would lack the path to OAR's runtimes that the owner requires ([DH-ADR-23](../design.md#dh-adr-23)). Six features are ported at P2, the two mods packages are dropped, and six packages are merged into components this or another area already designs.

## 2. Vocabulary

| Term | What it is | Why it exists |
|---|---|---|
| **Hook** | An external program the host runs at a lifecycle point, with a JSON description of the event on its standard input. Its exit code and output are its answer. | A person's own checks (a linter, a deny-list, a note for the model) run without being written as harness code. |
| **Lifecycle point, gating point** | A named moment at which hooks fire (session start, prompt submitted, before and after a tool, the turn about to stop, a subagent starting or ending, session end). The two gating points, `UserPromptSubmit` and `PreToolUse`, decide whether something happens. | A hook file selects moments by name; only at a gating point does a hook that could not answer need a fail-closed rule. |
| **Dialect, matcher, hook source** | A dialect is one of two published shapes for hook files, payload field names and matcher rules: `claude-code` or `codex`. A matcher is a pattern that selects by tool name or session source. A source is one hook file plus how it is trusted and where its commands run. | Existing files and scripts are written for one dialect; one file can hold a hook for `bash` only; trust is decided per file, not per command. |
| **Reviewer** | A model request that classifies one pending tool call as low, medium or high risk and allows or denies it. | Stands in for a person's approval in the `auto` permission preset. |
| **Delivery, rule, ingress** | A delivery is one verified event from an outside service. A rule is operator configuration that turns a matching delivery into a request for a new session. The ingress is the network listener that receives deliveries. | Three parts with different trust: the sender is anyone, the rule is the operator's, the listener is exposed. |
| **Unattended session** | A session nobody is connected to: no answerer is bound, so every question to a person is answered "no" ([DH-O-7](../design.md#dh-o-7)). | States what a webhook session may do. |
| **Round, handoff** | One fresh child agent in a ralph run; the bounded report it leaves for the next one. | The loop's unit of work and its only memory besides the workspace. |
| **OAR, runtime, bridge child** | OAR is a JavaScript library that drives several vendors' agent programs; each is a runtime. The bridge child is the operator's Node running the operator's OAR, started and owned by the host ([../libs/botiverse-oar.md](../libs/botiverse-oar.md)). | The owner's required path to those runtimes. |
| **Control** | Which party may type into an agent's terminal: `agent` until a person types, then `person`. | Two writers in one terminal would interleave input and share the person's sign-ins. |

### 3.2 Behaviour

- **Hooks.** A bridge parses one hook file when it loads; a read or parse failure logs a warning and registers nothing (`x/hooks-claude-code/src/index.ts:110-125`). At each point it selects the matching groups and runs each command through the shell executor with the event as JSON on standard input (`x/hook-protocol/src/runner.ts:74-87`). Exit 2 blocks, with standard error as the reason; exit 0 may carry a JSON object with a decision, a reason and extra context; every other exit, and a hook that could not start, is a non-blocking error (`x/hook-protocol/src/codec.ts:66-86`, `runner.ts:96-104`). Several answers merge as deny over ask over allow (`x/hook-protocol/src/merge.ts:35-52`). The points map onto harness events: `agent/created`, `agent/pre-step`, `tools/pre-execute`, `tools/post-execute`, `agent/turn-stopping`, `subagent/start` and `subagent/end` (`x/hooks-claude-code/src/index.ts:212-311`). A blocking Stop hook steers, which forces another step (`:284-291`). Each run inside a turn leaves a `hook/invoked` and `hook/result` pair in the log (`x/hook-protocol/src/events.ts:75-104`). A hook's `allow` approves nothing, and a rewritten input is logged and ignored (`x/hooks-claude-code/src/index.ts:184-186`, `:250-252`).
- **Claude Code mods.** `defineMod` wraps a mod as a cordis plugin; its handlers run as middleware around nine events and around other mods' host calls (`x/claude-code-mods/README.md:62-72`). The `$` object gives a mod commands, tools, prompt submission, session facts, storage, timers, files, processes, HTTP and the process environment (`:83-97`). The module runs inside the host "with its full authority" (`:99`). One band per session is drawn from the first mod whose render handler returns a tree; the client renders it and sends button presses back (`:79`).
- **Auto review.** Selecting `auto` sets the full-access sandbox with the `ask` approval policy (`.agents/notes/implemented/feature/2026-09-24-auto-review-user-approval-fallback.md:15`). A listener placed first on `tools/pre-execute` sends the fixed policy, the session's sourced instructions and action history, and the pending call to the session's own model (`x/auto-review/src/index.ts:741-781`; `x/auto-review/README.md:80`). Allow runs the body. A denial becomes a question to the person under `ask` and a final denial under `never`; a reviewer failure fails the call (`README.md:66`). Only text whose recorded source is the user counts as instruction (`.agents/notes/implemented/feature/2026-10-18-headless-auto-review.md:15`). The reviewer's prompt, risk and answer are not persisted (`README.md:119`).
- **Webhooks.** The GitHub adapter accepts `POST application/json`, reads the body under a limit, requires three headers, resolves the secret, verifies the signature over the raw bytes, parses, dispatches and answers 202 (`x/webhook-github/src/handler.ts:86-122`). The runtime starts every rule of that provider kind independently and returns before any settles (`x/webhook/src/index.ts:126-162`). A rule is "arbitrary trusted code" that returns nothing or one session request (`x/webhook/README.md:28`). The runtime then validates the presets, resolves or creates the workspace, creates an agent, attaches the session, applies permission and title, and queues the prompt with source kind `webhook`; that queueing is the commit point (`x/webhook/src/session.ts:100-139`). The guide mounts the route on a second web server so that exposing it does not expose the UI (`docs/subsystems/webhook.md:37`).
- **The ralph loop.** The tool submits a fixed JavaScript workflow script to a workflow engine; each round starts one fresh child with the objective, the round number and the previous report, and the loop ends on `complete`, `blocked` or the round cap (`x/tool-ralph/src/index.ts:91-177`). The provider must give structured output and must not inherit the parent conversation (`:224-230`). Guidance tells the model to use it only on a person's explicit request (`x/tool-ralph/README.md:115`). It differs from a goal, which keeps one session working: a round has no conversation, only the workspace and one bounded report (`README.md:12`, `:36`).
- **The OAR provider.** Described step by step in [../libs/botiverse-oar.md §2.1](../libs/botiverse-oar.md). The tool builds its `runtime` enumeration from configured aliases and refuses providers that continue or inherit context (`x/tool-subagent-oar/src/index.ts:30-46`, `:87`).
- **Terminals.** The six tools forward to `ctx.terminals` with the calling agent as owner; a background send registers a job (`x/tool-terminal/src/index.ts:171-401`, `:260-271`). The panel backend opens each agent terminal as a sidebar terminal. The person's first typed input takes control: afterwards agent sends and signals fail, reads continue, and closing only releases the agent's handle (`x/terminal-panel/src/session.ts:332`, `:365-368`). Subagents are refused (`x/terminal-panel/src/backend.ts:100`). `user_terminal_list` and `user_terminal_read` read terminals the person opened and are on by default (`x/terminal-panel/src/index.ts:39`; `README.md:66`).

### 3.3 Failure, retry, rollback and cleanup upstream

- **Hooks.** A failing hook never stops a turn: every failure becomes a contained outcome (`x/hook-protocol/README.md:77`). Disposing a bridge aborts running hooks and drains them (`x/hooks-claude-code/README.md:101`). A hook that asks the run to halt is recorded and nothing happens (`x/hook-protocol/README.md:130`); nothing caps a Stop hook that always blocks (`x/hooks-claude-code/src/index.ts:283`).
- **Webhooks and the rest.** A rule that throws is logged and its siblings run; unloading aborts and waits for callbacks but cannot stop code that ignores the signal (`x/webhook/README.md:74`). A crash loses deliveries that had not queued a prompt, and a repeated delivery creates a second session (`:71-72`). A failure after attachment detaches the workspace and disposes the agent, best effort; a workspace created on the way is kept (`x/webhook/src/session.ts:140-153`; `README.md:75`). Unloading auto review while the host runs moves live `auto` sessions to full access with no reviewer (`x/auto-review/src/index.ts:794`). A ralph child that fails ends the run with the failed round and the last good report; nothing is retried (`x/tool-ralph/README.md:166`). OAR owns the native processes, so the harness's cleanup does not reach them (`x/subagent-oar/README.md:163`).

```go
package hooks
type Output struct { // one hook's decoded answer; a failure is a value here, never a Go error
    Exit *int; Decision Decision // None | Deny | Ask (Ask only at PreToolUse): there is no Allow and no field for replacement arguments or output
    Reason, Context, Notice string; Halt bool; HaltReason string; Failure Failure // none|start|timeout|killed|oversize
}
type Service interface {
    Sources() []SourceStatus                                     // file, dialect, trust state, load diagnostics, unsupported entries found
    Trust(ctx context.Context, path string, digest Digest) error // an owner action; writes one entry to the writable config layer
    Run(ctx context.Context, c Command, stdin []byte, o RunOptions) (Output, time.Duration) // also runs webhook rule commands
}
package webhook
type Delivery struct{ Kind, Source, ID, Event string; Payload json.RawMessage; ReceivedAt time.Time } // built only by an adapter, after verification
type Runtime interface {
    Dispatch(ctx context.Context, d Delivery) (accepted bool, err error) // records the delivery, then runs matching rules in the background
    Records(page Page) ([]Record, error)                                 // received | no-match | admitted{sessions} | failed{category}
}
```

`x/oar` implements A12's `Runner` and `ExternalRun` exactly as [subagent-team.md §6.1](subagent-team.md) writes them and declares `{Continuable: false, InheritsContext: false, Preset: false, ModelOptions: false, CanAsk: false}`. No package here defines an interface another area must implement.

### 6.2 Contracts

**The hook protocol.** One process per hook per event. Standard input is one JSON object (`claude-code` adds a newline, `codex` does not: `x/hooks-codex/src/index.ts:152`). The environment is the scrubbed environment of the one process starter plus `CLAUDE_PROJECT_DIR` for the `claude-code` dialect; the working directory is the session's current directory. A hook receives **no call token**, so it cannot call tools ([DH-ADR-8](../design.md#dh-adr-8)).

| The hook's outcome | Meaning |
|---|---|
| Exit 0 | If standard output is a JSON object, a structured answer: `continue`, `stopReason`, `systemMessage`, `decision: "block"`, `reason`, and `hookSpecificOutput` with `hookEventName` (must name the firing point, or the block is ignored), `permissionDecision` (`deny` or `ask`; `allow` is read as no decision), `permissionDecisionReason`, `additionalContext`. Any other output is context at `SessionStart` and `UserPromptSubmit` and ignored elsewhere |
| Exit 2; any other exit code | Exit 2 blocks, with standard error as the reason. Any other code is the script's own "error, do not block": the action proceeds and the error is logged |
| Could not start, timed out, was killed, or wrote more than `maxOutputBytes` | The host got no answer: `onFailure` applies ([ADR-2](#dh-adr-xhooks-2)) |

Answers of the hooks that matched one event merge as deny over ask over none, in any order; context is joined in file order; the first `continue: false` wins. Context reaches the model as a logged message with source `{kind: "hook", source, point}`, at most `maxContextBytes`. `continue: false` at any point in a turn cancels that turn through `Agent.Cancel` with cause `extension`, inbox kept, and `stopReason` as the recorded reason. Nested calls from the tool command line pass `tools.Decide` and `tools.Shape` like any call, so hooks see them too.

| Point | Attached to (owner) | Matcher subject | A hook may | A hook may not |
|---|---|---|---|---|
| `SessionStart` | `agent.Created`, ordered and so awaited before the first turn (A02); the listener never returns an error | session source | add context | fail creation, or delay it past its timeout |
| `UserPromptSubmit` | `agent.PreStep`, when the claimed batch holds a message this component did not write | none | `Reject` the prompt (the turn ends `blocked`); add context after it | rewrite or hide the prompt |
| `PreToolUse` | `tools.Decide` (A03); the listener always calls downstream and returns the stricter answer | tool name, and its Claude Code alias in that dialect | `Deny`, `Ask`; add context, delivered at the same call's `tools.Shape` | allow, rewrite arguments |
| `PostToolUse`, `PostToolUseFailure` | `tools.Shape`, by the outcome | tool name | `Block` with feedback; add context | replace content or value |
| `Stop` | `agent.OnTurnStopping` | none | `KeepOpen` with a reason, at most `maxStopContinuations` times in a row; `stop_hook_active` is true after the first | keep a turn open past A02's budget |
| `SubagentStart`, `SubagentStop`, `SessionEnd` | `subagent.Started`, `subagent.Settled` (A12); `agent.Disposed` | provider name; none | observe; a start hook may add context to a local child | block or steer |

**Auto review.** The component adds the preset `auto` (sandbox `danger-full-access`, approval `ask`), which [interaction-credentials.md §6.2](interaction-credentials.md) reserves for it. For a session whose preset is `auto`, its `tools.Decide` listener appends `autoreview/requested{call, asOf}`, builds the reviewer request from that event with A01's `RequestFrom`, sends it on the session's current route within `autoreview.Config.timeout` (120 s), and appends `autoreview/decided{call, risk, decision, reason, failure}`. Valid answers are `low` and allow, `medium` and allow or deny, `high` and deny. Allow calls downstream. A denial under `ask` returns `Ask{reason}` only after downstream allowed; under `never` it returns `Deny` with code `autoreview/denied`. A malformed answer, a provider failure or a timeout is `Deny` with code `autoreview/failed`; nothing is retried. Guards still run afterwards, and a nested call is reviewed like a direct one.

**Webhooks.** A rule is one configuration entry: `id`, `kind`, `source`, `events`, `where` (a list of `{pointer, in}` conditions on the payload, all of which must hold; a missing field is false), and either `session` (`workspace`, `title`, `preset`, `permission`, `model`, `prompt`, `include`: payload pointers copied into a block labelled as untrusted data; an absent one fails the rule) or `command` (an argument list run by the hook runner with the delivery on standard input, which prints one session request or nothing). The GitHub ingress answers in upstream's order and with upstream's codes: 405, 415, 413, 400 for a missing or repeated header, 503 for an unavailable secret, 401 for a bad signature, 400 for a body that is not a JSON object, 202 once the delivery is recorded ([../libs/octokit-webhooks.md](../libs/octokit-webhooks.md), requirements R1 to R3); 429 when `maxPerHour` is exceeded.

**What an unattended session may do.** (1) Its permission preset must be in `allowedPresets`, by default `read-only` and `workspace-write`; a rule naming another preset is a load error. (2) No answerer is bound, so every `Ask` ends as `approval/unavailable`: nothing is escalated and no session grant can be created, until an owner opens the session in the browser and claims it under A17's rule. (3) Its prompt has source `webhook`, which is never instruction authority for the reviewer. (4) Hooks, guards, the turn budget and the sandbox apply as in any session. (5) At most `maxActive` webhook sessions run at once; further requests are recorded as `failed{capacity}`.

## 7. Decisions

<a id="dh-adr-xhooks-1"></a>
### DH-ADR-XHOOKS-1 Hooks are a second, narrower extension mechanism: operator-configured commands with a closed set of answers
- **Decision.** A hook is not a plugin. One compiled-in component runs commands named in operator configuration at nine points and maps each answer onto the closed decisions other areas define: `Deny` or `Ask` before a tool, `Block` after it, `Reject` of a prompt, `KeepOpen` at the stop, added context, and a halt. A hook cannot allow, cannot change arguments, content or values, cannot choose its message source, and gets no call token. Only command handlers run. A plugin directory's hook file is never read by itself; the operator lists it as a source.
- **Why.** The plugin protocol offers no interception because "an untrusted process must not be able to return `Allow`" ([extensions.md §6.2](extensions.md)). Hooks do not weaken that: their trust comes from configuration, not from a manifest, and their answers can only restrict or annotate. They also fit Go with no adaptation, since a hook was always a separate program.
- **Tradeoff.** Two ways to extend the host. Scripts that rely on `allow`, `updatedInput` or `updatedToolOutput` lose that effect; `http`, `mcp_tool`, `prompt` and `agent` handlers are listed and skipped, because the first sends data off the machine ([DH-ADR-9](../design.md#dh-adr-9)) and the last two are model calls outside the log. Matchers use Go's RE2 syntax, so a pattern with a look-ahead fails to load with a diagnostic.
- **Serves.** [DH-O-6](../design.md#dh-o-6), [DH-O-3](../design.md#dh-o-3), [DH-O-4](../design.md#dh-o-4). **Verified by.** DH-T-XHOOKS-1, DH-T-XHOOKS-3, DH-T-XHOOKS-4, [DH-E-XHOOKS-1](#dh-e-xhooks-1).

<a id="dh-adr-xhooks-2"></a>
### DH-ADR-XHOOKS-2 A hook source is trusted through configuration, and a hook that could not answer denies at the two gating points
- **Decision.** (a) A source listed in an operator layer is trusted. It runs under the session's sandbox policy unless its entry says `confine: none`, in which case it runs unconfined as the user, through the one process starter with a trusted launch. (b) With `discoverProject`, a hook file in a session's workspace runs only after an owner approved its exact bytes: the digest is stored in the writable layer, a changed file is untrusted again, and such a source runs under the session's sandbox policy (`confine: session`). (c) An exit code other than 0 or 2 keeps the protocol's meaning, "do not block". A hook that could not start, timed out, was killed or exceeded the output bound denies at `UserPromptSubmit` and `PreToolUse` unless `onFailure: proceed` is set.
- **Why.** A file in a cloned repository is someone else's commands; running it unseen would be code execution by checkout. A stored digest is trust in a file, like a plugin grant, not an approval rule across sessions ([DH-ADR-16](../design.md#dh-adr-16)). Upstream treats every failure as non-blocking (`x/hook-protocol/src/runner.ts:96-104`); a deny-list hook whose interpreter is missing would then silently stop protecting.
- **Tradeoff.** A broken hook path blocks every tool call until it is fixed; the denial names the hook, and `onFailure: proceed` restores upstream's behaviour. A hook with `confine: none` is as powerful as the user. Decided by the owner ([DH-ADR-31](../design.md#dh-adr-31)): an operator hook runs confined unless the operator writes `confine: none` for that hook source. Scope boundary of this record: a hook source is the JSON hook file both products share, at a path the operator names; hooks written inline in Codex's `config.toml` are not read, only synchronous command handlers run (an asynchronous hook cannot answer the decision it was asked), and Codex's `statusMessage` and `commandWindows` fields are ignored. Scope boundary of this record, Claude Code's fields: a hook's `suppressOutput` and `terminalSequence` flags are not applied, because they address a terminal interface this product does not have, and `transcript_path` is empty unless the hook source sets `transcript: true`, because the session lives in a database ([DH-ADR-PERSISTENCE-3](../upstream/session-and-persistence.md#dh-adr-persistence-3)) and writing an export file on every hook run is a cost and a copy of private data that each source must opt in to.
- **Serves.** [DH-O-7](../design.md#dh-o-7), [DH-O-6](../design.md#dh-o-6). **Verified by.** DH-T-XHOOKS-2, DH-T-XHOOKS-5, [DH-E-XHOOKS-1](#dh-e-xhooks-1).

<a id="dh-adr-xhooks-3"></a>
### DH-ADR-XHOOKS-3 The Claude Code mods bridge and its band are not built
- **Decision.** `claude-code-mods` and `client-ui-claude-code-mods` are dropped, with the `claudeCodeMods` service and the bridge's configuration. What a mod could do has these homes: guarding a tool call, adding context and reacting to a stop are hooks; tools and commands are a plugin process ([extensions.md](extensions.md)). Drawing above the prompt, rewriting a prompt and answering a tool call in the tool's place have none.
- **Why.** A mod is a JavaScript module that must run in the host's process with the `$` interface as live objects (`x/claude-code-mods/README.md:28`, `:99`). The Go host loads no code and embeds no interpreter ([DH-ADR-4](../design.md#dh-adr-4), [DH-ADR-8](../design.md#dh-adr-8)). Inference: a Node sidecar speaking an interception protocol would be the very thing the plugin protocol refuses, for a bridge upstream calls an alpha demonstration that serves a fraction of the reference (`:12`, `:205-206`).
- **Tradeoff.** Existing mods do not run, and nothing third-party can draw in the UI. A recorded exception to [DH-ADR-1](../design.md#dh-adr-1). Recommended default, not confirmed by the owner ([§10](#10-open-questions-and-limitations), item 5).
- **Serves.** [DH-O-11](../design.md#dh-o-11), [DH-O-16](../design.md#dh-o-16). **Verified by.** The `dropped` and `not-applicable` ledger rows that link here.

<a id="dh-adr-xhooks-4"></a>
### DH-ADR-XHOOKS-4 Auto review is kept as a policy listener whose request and verdict are logged, and whose removal tightens
- **Decision.** Port the three implemented decisions: a fixed policy, one review per call including nested calls, authority by recorded source, a denial that asks under `ask` and is final under `never`, and a failure that is never a denial. Change two things. The reviewer request is an auxiliary request built from one committed event, and its verdict is a committed event. When the component unloads while the host runs, live `auto` sessions move to `read-only`, and a session recorded as `auto` cannot run tools until the component is back or an owner picks another preset.
- **Why.** The owner dropped a browser layer because its second model left no trace in the session log ([DH-ADR-24](../design.md#dh-adr-24)); a reviewer that decides what runs with full access must be reconstructable ([DH-O-4](../design.md#dh-o-4)). Upstream's fallback on unload is full access with no reviewer (`x/auto-review/src/index.ts:794`), which fails open.
- **Tradeoff.** One more model request and two more events per call. The reviewer is a fallible model, not a boundary: an allowed call runs with full access, and what a script does beyond its visible text is not reviewed. Foreign agents started by delegation keep their own permission systems.
- **Serves.** [DH-O-6](../design.md#dh-o-6), [DH-O-7](../design.md#dh-o-7), [DH-O-4](../design.md#dh-o-4). **Verified by.** DH-T-XHOOKS-6, [DH-E-XHOOKS-2](#dh-e-xhooks-2).

<a id="dh-adr-xhooks-5"></a>
### DH-ADR-XHOOKS-5 Webhook rules are configuration, the ingress is its own listener, and an unattended session cannot be widened
- **Decision.** A rule exists only in an operator layer, as conditions and a session request or as a command the host starts and stops. The ingress is a second instance of A18's listener whose only mount is the adapter's `callback` route; the UI listener never serves it. The signature is verified over the raw body before parsing, with the standard library ([../libs/octokit-webhooks.md](../libs/octokit-webhooks.md)). A delivery is recorded before 202 and its record decides whether a redelivery runs. The five limits of [§6.2](#62-contracts) bound what the session may do.
- **Why.** [DH-ADR-WIRE-12](../upstream/wire-and-api.md#dh-adr-wire-12) fixes the wire shape and leaves de-duplication to this area. The payload is text anyone who can open a pull request controls, so it is labelled as data and the session must not be able to ask its way to more access. Rule code inside the host cannot be stopped (`x/webhook/README.md:74`); a child process can.
- **Tradeoff.** Rules are less expressive than code unless the operator writes a command. There is still no queue and no completion report: the provider's redelivery is the retry, and the record names the session to look at. One provider. Scope boundary of this record: the GitHub endpoint accepts `application/json` bodies only and answers a form-encoded delivery with status 415, because GitHub lets the operator choose JSON, and one content type keeps this internet-facing handler to one decoder that runs only after the signature over the raw body was verified.
- **Serves.** [DH-O-13](../design.md#dh-o-13), [DH-O-7](../design.md#dh-o-7). **Verified by.** DH-T-XHOOKS-7, DH-T-XHOOKS-8, [DH-E-XHOOKS-3](#dh-e-xhooks-3).

<a id="dh-adr-xhooks-6"></a>
### DH-ADR-XHOOKS-6 Ralph is a Go loop on the subagent seam; it is neither a workflow nor a goal
- **Decision.** Keep the tool and port it as a loop that calls `subagent.Runtime.Start` once per round with an output schema for the report and `Delivery: Caller`, and disposes each activation before the next. It uses no workflow engine. It is not merged into goals: a goal keeps one session and its context, and A13 carries "one goal, one session" on purpose, naming fresh-agent attempts as delegation ([jobs-schedule-goal-plan.md §5](jobs-schedule-goal-plan.md)). The tool is denied by a guard unless the turn is a human turn (`authority.HumanTurn`) and the caller is not a delegated agent.
- **Why.** The script engine was the only reason for the isolated engine, the text-only error path and the missing budgets. Fresh context per round is a different remedy from a goal's persistence: it trades memory for a clean window.
- **Tradeoff.** Two long-running mechanisms remain for a person to choose between. Completion is still the worker's own claim, and a run still blocks its tool call. Scope, recorded here (register section 5.2; recommended default, not confirmed by the owner): ralph has no evaluator. No second agent or check judges whether the objective is met, as area A13 records for goals (`DH-ADR-JOBS-10`); the bound on rounds and the person reading the result are the control.
- **Serves.** [DH-O-9](../design.md#dh-o-9). **Verified by.** DH-T-XHOOKS-9, [DH-E-XHOOKS-2](#dh-e-xhooks-2).

<a id="dh-adr-xhooks-7"></a>
### DH-ADR-XHOOKS-7 The OAR provider is a `Runner` on the subagent seam, and its selector is the shared delegation tool
- **Decision.** Confirm the path of [DH-ADR-OAR-1](../libs/botiverse-oar.md#dh-adr-oar-1): `x/oar` registers one `Runner` per configured instance, starts the bridge child through A12's `external` lifecycle and the one process starter, and meets requirements `DH-LIB-OAR-R1` to `-R11`. Upstream's `subagent_oar` tool is A12's delegation tool with `targets`. The bridge script (entry 1 of that decision) is the entry built; the OAR command line stays an open question.
- **Why.** The owner keeps the bridge ([DH-ADR-23](../design.md#dh-adr-23)). A12 owns the seam and already lists the `oar` row, so this area adds a provider and no contract.
- **Tradeoff.** **Unconfirmed, stated plainly:** the OAR command line and its output; which OAR releases the script works with (verified only as upstream uses 0.67.0, patched); whether an unpatched OAR lets Claude Code be restricted; how the operator's Node resolves the package; five of seven runtimes; whether the native agent can run inside the harness sandbox. Delegating hands the task to another vendor's agent, which talks to its own service: the operator's instance entry is the opt-in ([DH-ADR-9](../design.md#dh-adr-9)).
- **Serves.** [DH-O-9](../design.md#dh-o-9), [DH-O-10](../design.md#dh-o-10). **Verified by.** DH-T-XHOOKS-10, `DH-T-OAR-1` to `-4`, [DH-E-XHOOKS-4](#dh-e-xhooks-4).

<a id="dh-adr-xhooks-8"></a>
### DH-ADR-XHOOKS-8 One terminal service: six tools on it, control passes to the person and does not come back, and reading the person's terminals is opt-in
- **Decision.** `terminal-panel` and `terminal-bundle` are merged away: A09's `terminal.Service` is the only backend and a browser already attaches to it, so the six tools work in every profile. An agent terminal starts under `agent` control. The first input the terminal island marks as typed by a person sets `person` control: agent sends and signals fail with `terminal/person-control`, reads continue, `terminal_close` releases without ending the shell, and ownership passes to the session's user-terminal record. There is no hand-back. Commands inside cannot request escalation. `user_terminal_*` are off by default.
- **Why.** After a person has typed, the shell may hold a `sudo` or `ssh` sign-in; giving input back would hand the model that authority with no approval (`.agents/notes/implemented/feature/2026-10-12-agent-terminal-panel.md:33`). A person's screen can show secrets, and what the model reads is logged and sent to the provider.
- **Tradeoff.** The model must open a new terminal after a takeover. A person who takes one over gets the agent's bare, confined shell, not their own profile. Subagents may open terminals here, unlike upstream; showing them needs the roster to cover a session's tree. Scope boundary of this record: a read of a person's terminal returns the screen as it is at that moment and does not wait for the program to become idle or for new output, because a person's terminal gives no readiness signal and a read must not block the turn.
- **Serves.** [DH-O-10](../design.md#dh-o-10), [DH-O-12](../design.md#dh-o-12), [DH-O-7](../design.md#dh-o-7). **Verified by.** DH-T-XHOOKS-11, [DH-E-XHOOKS-5](#dh-e-xhooks-5).

## 10. Open questions and limitations

1. **Assumed of [execution.md](execution.md) and [api.md](api.md) (requests sent).** A control state per agent terminal, set when A19's socket delivers input marked as typed; agent `Send` and `Signal` refused in `person` control and `Close` reduced to a release; ownership passing to the user-terminal record; environment entries on `Open` and a default shell start that runs no user start-up files; a text read of a user terminal's screen; a roster that covers a session's tree. [api.md §10](api.md) item 6 asks A09 the first question and [execution.md](execution.md) does not answer it: this document specifies the rule, and the two areas place it.
2. **The terminal fence follows [execution.md](execution.md).** Area A09 owns terminals, and its §6.2 refuses a sandbox-mode change while the owner has a terminal. This document conforms: a terminal a person took over counts, and the refusal names it so that the person can close it. The upstream panel note argues that such a terminal should not count; that is requested of A09, not assumed here.
3. **Assumed of [host-telemetry.md](host-telemetry.md) (request sent).** A second instance of `host.listen` with its own address and TLS, whose only mount is the ingress, and which mints no launch token. If the component cannot be instantiated twice, the ingress needs a listener of its own with the same admission steps.
4. **Settled, and still assumed.** Settled by [agent-loop.md](agent-loop.md) and [tools.md](tools.md): source kind `user` is set only by carriers, which the reviewer relies on; a listener may call `Agent.Cancel` for its own turn; `tools.Shape` runs for a denied call, so pre-tool context is not lost; log-only events outside a turn are legal. Still assumed (requests sent): [execution.md §6.1](execution.md) accepts a trusted launch for an operator hook with `confine: none` although an agent's event triggered it; [interaction-credentials.md](interaction-credentials.md) lets a component tighten a session to `read-only` when it unloads ([ADR-4](#dh-adr-xhooks-4)), where today only an owner switches a permission preset.
5. **Decided, and recommended defaults.** Decided by the owner: an operator hook runs confined unless its entry says `confine: none` ([DH-ADR-31](../design.md#dh-adr-31), [ADR-2](#dh-adr-xhooks-2)). Recommended defaults, not confirmed by the owner: (a) the Claude Code mods bridge is not built ([ADR-3](#dh-adr-xhooks-3)), an exception to [DH-ADR-1](../design.md#dh-adr-1) made by this area; (b) the OAR provider drives an operator-installed OAR on Node ([ADR-7](#dh-adr-xhooks-7)), and nothing of Node enters the `dsh` binary; (c) ralph has no evaluator ([ADR-6](#dh-adr-xhooks-6)). **Unconfirmed until run:** everything [ADR-7](#dh-adr-xhooks-7) lists, and [../libs/botiverse-oar.md §7](../libs/botiverse-oar.md); the supported release range can only be set by running [DH-E-XHOOKS-4](#dh-e-xhooks-4).
6. **Limits kept.** The 35 carried units of [§5](#5-tech-debt-and-its-resolution). Hooks remain a compatibility subset; the reviewer is a model; a webhook has no queue; ralph trusts the worker; a foreign agent keeps its own permissions and transcripts; a terminal has inferred readiness and no hand-back. Timeouts, caps and windows in [§6.2](#62-contracts) are judgements, not measurements. Upstream inconsistency found: the Claude Code bridge's README says `SessionStart` is "awaited ... before the first turn" (`x/hooks-claude-code/README.md:89`) and also that it "runs detached, so context can miss the first request" (`:176`).

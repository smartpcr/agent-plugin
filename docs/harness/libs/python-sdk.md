## 1. What it is and why upstream needs it

The Python SDK lets a Python program drive the harness: start it, send a prompt, watch
what the agent does, answer its approval requests and questions, and read the final
answer. A data pipeline, a test rig or an evaluation script uses it instead of a person
typing into the user interface. Without it a Python user would have to write their own
process launcher and protocol client.

It has two halves. The **client** (`python/sdk`, distribution `deepseek-harness-sdk`) is
Python code. It starts the harness as a child process and talks to it over the child's
standard input and output. The **runtime wheel** (`python/sdk-runtime`, distribution
`deepseek-harness-runtime-bin`) is how the harness itself reaches the user's machine: a
Python package that contains no logic of its own, only the `dsh` executable for one
platform (`python/README.md:9-12`). Upstream's harness is a Node application, so that
executable is the whole Node program and its dependencies packed into one file.

| Term | What it is | Why it exists |
|---|---|---|
| **Wheel** | The installable archive format of Python packages: a zip file with a metadata folder. Its file name carries a *platform tag* that tells the installer which machines it fits. | It is what `pip install` downloads and unpacks. |
| **Pure wheel, platform wheel** | A pure wheel (`py3-none-any`) holds only Python and fits every machine. A platform wheel holds machine code and fits one operating system and CPU. | The client is pure; the executable is not. |
| **Distribution, import package** | The distribution is the name given to `pip install`. The import package is the name written after `import`. | They differ upstream and both change in the Go design. |
| **SDK protocol** | Newline-delimited JSON-RPC 2.0 on the child's standard input and output: one JSON message per line ([upstream/wire-and-api.md §5](../upstream/wire-and-api.md#5-sdk-protocol)). | No port and no credential: whoever started the process owns it. |
| **Host request** | A request the harness sends to the client and waits on, such as "may I run this command?". | Approvals and questions need an answer from the embedding program. |
| **Harness home** | The directory with one installation's sessions, configuration and secrets ([design §2](../design.md#2-vocabulary)). | The SDK must never silently share the user's interactive home. |
| **Close ladder** | The ordered attempts to stop the child: ask, close its input, terminate, kill. | A library must not leave a process behind. |

### 2.3 How the client launches the runtime and talks to it

1. **Find the executable.** `dsh_bin` if given, otherwise the runtime wheel's
   `resolve_bundled_launch_args()` (`client.py:597-608`).
2. **Require a home.** `dsh_home` or a non-empty `DSH_HOME`; otherwise a `ValueError`
   before anything starts. The client never falls back to `~/.dsh` (`client.py:610-618`).
3. **Start the child** as `dsh --profile <profile> [--patch <file>]...` with
   `subprocess.Popen`, text pipes, line buffering and the parent's environment plus the
   caller's overrides (`client.py:85-99`, `:620-625`). `base_url` and `api_key` travel as
   environment variables of the child (`api.py:123-127`).
4. **Read on threads.** One daemon thread reads standard output and routes each line:
   a response to its waiter, a host request to the question callback or the request
   queue, a notification to its subscribers. A second thread keeps the last 400 lines of
   standard error for diagnostics (`client.py:63`, `:431-505`). A line that is not JSON
   is skipped without notice (`client.py:439-442`).
5. **Handshake.** `initialize` sends the workspace, provider, model and optional limits,
   bounded at 30 seconds; a failure closes the child and adds the standard-error tail to
   the exception (`client.py:35`, `:151-199`). No protocol version is exchanged.
6. **Close.** Request `shutdown` (1 second by default), close standard input, wait,
   terminate, wait, kill (`client.py:37`, `:103-149`).

The wire protocol itself is described in
[upstream/wire-and-api.md §5](../upstream/wire-and-api.md#5-sdk-protocol).

### 2.6 Failure, retry and cleanup upstream

- A request timeout stops only the local wait. It does not cancel work in the runtime and
  does not close the client (`python/sdk/README.md:74`, `:146`). The wire has no cancel.
- A runtime that exits or closes its output fails every waiter, subscriber and pending
  question with `TransportClosedError` carrying the exit code and the standard-error tail
  (`client.py:507-520`, `:572-595`).
- The client never retries a request. A timeout or a failing observer "does not roll
  back runtime work or authorize an automatic retry" (`python/sdk/README.md:74`).
- A pending approval or question fails closed when the connection is lost; a late reply
  is discarded (`python/sdk/README.md:89`, `:140`).
- If the Python program dies without calling `close()`, the child sees end-of-file on its
  input and disposes itself
  (`.agents/notes/implemented/architecture/2026-07-10-single-file-executable-sdk-runtime-distribution.md:75`).
- Closing with the default 1-second budget may kill the runtime before it has flushed.
  Upstream keeps a manual script for this and says that a successful restore "does not
  establish a shutdown latency bound" (`python/development.md:69-75`).

### 4.3 The two wire decisions measured against the real SDK

[DH-ADR-WIRE-5](../upstream/wire-and-api.md#dh-adr-wire-5) and
[DH-ADR-WIRE-6](../upstream/wire-and-api.md#dh-adr-wire-6) hold up. Both are adopted
here. Reading the Python source adds seven points that neither states; items 1 to 5 are
requests to area A20, which owns the method set ([design §8, gaps](../design.md#8-conflicts-and-gaps-between-the-foundation-recommendations)).

1. **The run result must cover commands too.** WIRE-5 defines `session.run.completed` for
   a prompt's `messageId`. Python's `run()` also returns results for slash commands,
   identified by `commandId`, and a goal run ends only when the goal stops
   (`api.py:239-261`; `python/sdk/README.md:82`).
2. **Scoped notifications must say which session is the root.** `RunResult.events` holds
   root-session events only, while notifications cover the whole tree
   (`python/sdk/README.md:148`). With host-side scoping the client no longer keeps the
   tree, so each notification needs its root (or parent) session id.
3. **The method set is larger than WIRE-5's table of changes.** In use today:
   `session/query`, resume with a permission preset, working-directory get and set, and
   the `reasoningEffort`, `maxTokens`, `approvalRequests` and `capabilities` fields of
   `initialize` (`client.py:167-179`, `:220-268`).
4. **The schema must list methods, not only types.** WIRE-6 says the models are
   generated. If the schema has no method table (name, direction, parameter type, result
   type), the method names stay hand-written and can still drift.
5. **The host needs a bounded exit after its input closes.** The ladder's last steps run
   in the client; if the client process is gone, only the host can end itself.
6. **"As upstream does" hides two distributions.** WIRE-6's per-platform wheel is kept,
   but as one distribution ([DH-ADR-PYSDK-4](#dh-adr-pysdk-4)).
7. **The Python client is not one-directional** ([§4.2](#42-upstream-decisions-judged),
   last row). This agrees with [DH-ADR-WIRE-4](../upstream/wire-and-api.md#dh-adr-wire-4),
   which has the SDK answer approvals by replying to a host request.

## 5. Go choice

**Decision.** `DH-LIB-PYSDK` is **own code**. The five Python dependencies are replaced as
follows, and no Go module is added: the two Go tools below use only the standard library
(`archive/zip`, `crypto/sha256`, `encoding/base64`, `encoding/json`, `text/template`,
`debug/elf`, `debug/macho`, `debug/pe`).

| Dependency | Go design | Disposition |
|---|---|---|
| `pydantic` | Wire types are generated as standard-library `dataclasses` with generated decode and encode functions ([DH-ADR-PYSDK-2](#dh-adr-pysdk-2)) | replaced |
| `hatchling` | A Go tool writes the wheel archives in the release job ([DH-ADR-PYSDK-5](#dh-adr-pysdk-5)) | replaced |
| `pytest` | The Python tests use the standard-library `unittest` runner. Most upstream tests cover product behaviour (commands, plan, goal) that the Go design tests in Go | replaced |
| `Pillow` | Not used: Office operations leave the Python package ([DH-ADR-PYSDK-7](#dh-adr-pysdk-7)) | dropped |
| `deepseek-harness-runtime-bin` | Folded into the one distribution: the Go binary sits inside each platform wheel ([DH-ADR-PYSDK-4](#dh-adr-pysdk-4)) | merged |

**Why.** `DH-LIB-PYSDK-R1`: every one of these is either a second copy of something the Go
side already owns (types, the build) or serves a feature that moves. A client with no
dependencies cannot conflict with whatever versions the user's own program pins.

**Options for wire types (`pydantic`).**

| Option | Pros | Cons | Verified facts |
|---|---|---|---|
| **Chosen: generated `dataclasses`, standard library only** | No dependency; one source of types; validation stays | We own a generator; users lose `model_validate` and `model_dump` on SDK types | Standard library; nothing to verify as a module |
| Keep `pydantic`, generate its models from the schema | Rich validation and familiar API | Keeps a compiled dependency (`pydantic-core`, `python/sdk/uv.lock:204`) and four packages in every user's environment; adds a Python code generator to the build | Not checked against the package index |
| Keep hand-written `pydantic` models | No generator | The drift upstream documents (`packages/sdk/protocol/README.md:152`) | n/a |
| No types: plain dictionaries | Smallest client | Violates `DH-LIB-PYSDK-R2`; errors surface in user code | n/a |

**Options for building wheels (`hatchling`).**

| Option | Pros | Cons | Verified facts |
|---|---|---|---|
| **Chosen: a Go wheel writer** | The release needs only the Go toolchain; all wheels come from one runner; output can be made byte-for-byte repeatable | We must follow the wheel format exactly; an index or installer may reject what a hand-written archive gets wrong | Not verifiable without running an installer and an upload: open question 4 |
| `hatchling` with a custom hook, as upstream | Standard tool; format details are its problem | Python, a build front end and the hook in the release job; the hook must override the inferred platform for every cross-built target anyway (`hatch_build.py:69`) | Upstream pin `1.32.0` |
| `hatchling` for the pure wheel, Go writer for platform wheels | Smaller own surface | Two build paths for one package | n/a |

**Tradeoff.** The project owns two small tools and their tests in exchange for a Python
side with no dependency and a release with one toolchain. If the wheel writer proves
unreliable against a real installer or index, the fallback is the second row
(`hatchling`), which changes the release job and nothing in the package.

## 6. Design notes

### 6.1 Shape

```
Python program
   |  imports
   v
Python client (pure Python, standard library)
   |  facade: Harness, Session, RunResult, handlers
   |  generated: wire dataclasses, method stubs, error codes, PROTOCOL_VERSION
   |  transport: child process, reader thread, request table, handler threads
   |
   |  newline-delimited JSON-RPC 2.0 on the child's stdin and stdout; stderr = diagnostics
   v
dsh (Go binary, "sdk" profile)   <- the same file as in the release archive,
                                    carried inside the platform wheel
```

| Piece | Language | Where (proposed) | Owner |
|---|---|---|---|
| Facade, transport, launcher, console shim | Python | `src/harness/clients/python/` | this spec |
| Generated protocol module | Python, generated | same directory, checked in | this spec |
| Generator | Go | `src/harness/internal/wire/pygen` | this spec |
| Wheel writer | Go | `src/harness/internal/release/pywheel` | this spec |
| SDK protocol: codec, message types, method table and the embedded schema file | Go | module `src/sdk`, packages `sdk/jsonrpc` and `sdk/protocol` (standard library only) | area A20 ([../areas/sdk-acp-typert.md](../areas/sdk-acp-typert.md)) |
| SDK server (the carrier) and the schema derivation | Go | `src/harness/internal/wire/sdkserver`, `internal/wire/protoschema` | area A20 |
| A Go client package for Go programs | Go | module `src/sdk`, package `sdk`; a Go program that drives the harness imports this module and nothing else | area A20 ([DH-ADR-PYSDK-1](#dh-adr-pysdk-1)) |

Inference: the paths are proposals inside the families of
[design §4.2](../design.md#42-go-module-layout); the coordinator may move them.

**Working names.** This document writes the distribution as `dsh-sdk` and the import
package as `dsh_sdk`. Inference: upstream's names (`deepseek-harness-sdk`,
`deepseek_harness`) belong to upstream's publisher, so this project should not reuse
them. The owner chooses the final names (open question 1).

### 6.2 The Python API

Synchronous, with threads, as upstream (`client.py:42-43`). Python 3.10 or newer, as
upstream (`python/sdk/pyproject.toml:10`).

| Object | Members | Notes |
|---|---|---|
| `Harness(home=..., cwd=..., provider=..., model=..., profile="sdk", overlays=(), dsh_bin=None, env=None, on_approval=None, on_question=None, tools=(), ...)` | context manager; `start()`, `close()`, `session(id=None)`, `resume(id, permission_mode=None)`, `run(input, session_id=None, on_event=None)`, `server_info` | Starts lazily. `home` is required ([§6.3](#63-launch-and-handshake)). |
| `Session` | `id`, `run(input, on_event=None)`, `prompt(input)`, `wait()`, `cancel()`, `close()`, `history(after_seq=0, limit=None)`, `get_working_directory()`, `set_working_directory(path)` | `cancel`, `close` and `history` are new: they are the methods WIRE-5 adds. |
| `RunResult` | `session_id`, `message_id`, `final_response`, `finish_reason`, `events` | Filled from the host's completion notice. `events` holds the root session's events of this run; collection can be switched off for long runs. |
| Event | `seq`, `time`, `type`, `data`, `ignorable`, `session_id`, `root_session_id` | The envelope is typed. `data` stays a dictionary: the set of event types is open, and typing every one would tie the client to one host build. |
| Handlers | `on_approval(request, cancelled) -> "allowed-once" \| "rejected" \| "cancelled"`; `on_question(request, cancelled) -> answer`; tool functions ([DH-D-PYSDK-5](#dh-d-pysdk-5)) | Each call runs on its own worker thread. `cancelled` is a `threading.Event`. |
| Errors | `HarnessError` (base), `TransportClosedError(exit_code, stderr_tail)`, `ProtocolError`, `RpcError(code, reason, message, data)`, `VersionMismatchError`, `RuntimeNotFoundError`, `SlowConsumerError` | `reason` is the `<domain>/<reason>` code of WIRE-5. All are exported. |
| `Client` (low level) | one generated method per protocol method, `request(method, params)`, `subscribe()` | For callers who manage the run boundary themselves. |
| Module functions | `runtime_path()`, `verify_runtime()` | [§6.4](#64-the-wheel-and-how-the-binary-is-found) |

**What stays in Python:** starting and stopping the child, framing, matching responses to
requests, calling handlers, typed access to data. **What does not:** deciding when a run
is finished, which session a notification belongs to, what the final answer is, or
whether an input is a command. Those are host facts
([DH-ADR-PYSDK-1](#dh-adr-pysdk-1)).

**Reading without blocking the host.** The reader thread never runs user code and never
waits on a consumer. Each run and each subscription has a buffer with a stated maximum.
If a consumer falls behind, that run fails with `SlowConsumerError`; the host is not
affected, and the caller can read what it missed with `history(after_seq)`. This
matters because a blocked reader would fill the pipe, and the host closes a connection
whose reader stalls (WIRE-5, "slow reader").

### 6.3 Launch and handshake

1. **Resolve the binary**: the `dsh_bin` argument, else the `DSH_BIN` environment
   variable, else the binary inside the installed wheel. Nothing else is searched: not
   `PATH`, not the network.
2. **Require a home.** `home` or a non-empty home variable in the child environment;
   otherwise an error before any process starts. Kept from upstream.
3. **Start the child** with the `sdk` profile and the ordered overlay files, in the launch
   form area A24 defines. The child inherits the parent's environment plus `env`. A
   provider key given to the client is placed only in the child's environment, never in
   its arguments or a file, as upstream (`api.py:123-127`). The host builds the
   environment of its own children separately
   ([DH-ADR-SECURITY-6](../upstream/security.md#dh-adr-security-6)).
4. **Handshake.** `initialize` carries the protocol version generated into the client,
   the client's description (`clientInfo`, which includes its `timeZone`) and
   the capability flags, which are derived from the handlers the caller registered: an
   approval handler turns on approval requests, a question handler turns on questions,
   declared tools are listed. The reply carries the host's protocol version and build
   version. A different protocol version raises `VersionMismatchError` and closes the
   child. A different *build* version is an error only for the bundled binary (it means a
   damaged install); with `dsh_bin` it is allowed, so a developer can run a local build.
5. **Bound.** The handshake has its own timeout (30 seconds by default, as upstream). A
   timeout closes the child and reports the profile and the standard-error tail.
6. **Names and bounds fixed by the protocol owner.** The session-create field that
   selects an agent preset is `agentPreset`. After end-of-file on its input the host
   exits within boot's `ShutdownTimeout` (20 seconds), which is the bound the client's
   close ladder relies on. The method table of area A20 governs
   ([../areas/sdk-acp-typert.md](../areas/sdk-acp-typert.md)); the generated Python
   module follows it.

### 6.4 The wheel and how the binary is found

One distribution, published as one wheel per release target plus one pure wheel:

| Wheel | Contains | Selected by the installer when |
|---|---|---|
| `dsh_sdk-<version>-py3-none-<platform tag>.whl`, one per target | The Python package, `dsh` (or `dsh.exe`) as package data with its executable bit, and a small manifest: version, target, size and SHA-256 of the binary | The platform tag fits the machine |
| `dsh_sdk-<version>-py3-none-any.whl` | The Python package only | No platform wheel fits. Starting then raises `RuntimeNotFoundError`, which names `dsh_bin` |

The release targets are those of
[DH-ADR-TOOLCHAIN-13](../upstream/toolchain.md#dh-adr-toolchain-13): Linux, macOS and
Windows on amd64 and arm64. Inference: a Go binary built without cgo has no dependency on
the C library, so one Linux binary can carry both the glibc (`manylinux`) and musl
(`musllinux`) tags; the exact tags, and the macOS minimum that the Go toolchain of the
release supports, must be read from a real build (open question 3).

**Integrity, at four points.**

| When | Check | What it catches |
|---|---|---|
| Release | The binary inside each wheel has the same SHA-256 as the binary in the release archive for that target; the wheel's `RECORD` lists the hash of every file; the wheel's own hash is published | A wheel built from different bytes than the release |
| Install | Inference: the installer compares the wheel with the hash from the index, and with the user's lock file when one is used. This is the installer's behaviour, not ours | A corrupted or substituted download |
| Every start | The binary exists, is executable and has the size the manifest states; the handshake versions match | A partial or mixed install, a missing executable bit |
| On demand | `verify_runtime()` recomputes the SHA-256 and compares it with the manifest and with `RECORD` | A changed binary |

The full hash is not recomputed at every start. Inference: it would add a noticeable
delay to each launch and protect nothing, because whoever can change the binary in the
install directory can change the manifest beside it.

**The `dsh` console command** is a few lines of Python that replace themselves with the
binary on POSIX and wait and forward the exit code on Windows, as upstream does
(`python/sdk-runtime/src/deepseek_harness_runtime/__init__.py:196-209`). Unlike upstream
it adds no home rule of its own.

**The wheel writer** takes the binary produced by the release build for a target, the
Python sources and the version, and writes the archive: package files, the metadata
folder (`METADATA`, `WHEEL`, `RECORD`, `entry_points.txt`, licence and third-party
notices), fixed timestamps and sorted entries. It refuses a binary whose file header
(operating system and CPU) does not match the target, a wheel over the size limit, and a
version that is not valid in Python's scheme.

### 6.5 Ownership, failure, retry, rollback and cleanup

**Ownership and access.** The `Harness` object owns the child process it started and is
the only thing that stops it. A `Session` object is access to a session, not ownership:
dropping it changes nothing, and the session's data belongs to the harness home. The
home belongs to the caller; the client never deletes it. A handler thread is owned by
the client and is told to stop through its event; the client cannot force it to end.

| Situation | What happens | What is undone, and what stays uncertain |
|---|---|---|
| No binary for this platform, or it is not executable or has the wrong size | `RuntimeNotFoundError` before a process starts, naming the fix | Nothing started |
| The handshake fails or times out | The child is stopped by the ladder; the error carries the exit code and the standard-error tail | No session was touched |
| Protocol version mismatch | `VersionMismatchError`; the child is stopped | Nothing |
| A request times out locally | `TimeoutError`. The work continues in the host; the client stays usable | **Uncertain:** whether the request was applied. The caller decides between `cancel()` and waiting. The client never resends |
| A handler raises or returns an invalid value | The host gets an error reply and treats it as a refusal | Fail closed; the turn continues with a denial |
| A handler ignores its cancellation event | Its late answer is not sent. `close()` waits a short, bounded time for handler threads and then returns | The thread may still run in the caller's process |
| A consumer falls behind | `SlowConsumerError` for that run or subscription only | Missed events are read again with `history(after_seq)` |
| The host exits or closes its output | Every waiter, subscription and handler event is failed with `TransportClosedError`. The object stays failed until `close()` | **Uncertain:** the outcome of tools that were running. After a new start, `resume(id)` shows the turn closed as interrupted ([design §5](../design.md#5-failure-retry-rollback-and-cleanup)). There is no automatic restart: only the caller knows whether to resend |
| `close()` | Ask, close input, wait, terminate, wait, kill, each bounded; it can be called twice | Events not yet flushed when a kill lands are lost; committed events survive |
| The Python process dies without `close()` | The child reads end-of-file on its input and ends itself within the bound area A20 sets | **Uncertain:** if the host hangs there, a process remains. Only the host can prevent that (open question 5) |
| A release upload stops half-way | Run it again, skipping files already present. A published file cannot be replaced | A wrong release is withdrawn on the index and superseded by the next patch version |

### 6.6 What a migrating user must do

Under [DH-ADR-2](../design.md#dh-adr-2) the Python API is redesigned
([DH-ADR-PYSDK-6](#dh-adr-pysdk-6)). In order:

1. Install the new distribution and remove both upstream ones. Change the import name.
2. Start with a **new, empty home**. Upstream sessions, profiles and patch files are not
   read by the store ([DH-ADR-2](../design.md#dh-adr-2)). Old sessions can be brought
   over later with the separate import command, which is one-way, reads upstream's
   current session format only and is scheduled after the core
   ([DH-ADR-11](../design.md#dh-adr-11)); until it is built there is no import.
3. Rename the entry points: `DeepSeekHarness` to `Harness`, `dsh_home` to `home`,
   `patches` to `overlays`, `start_session` to `session`, `resume_session` to `resume`,
   `on_user_question` to `on_question`.
4. Replace an approval loop over `next_request()` and `respond()` with an `on_approval`
   function, and remove `approval_requests=True`.
5. Stop calling `model_validate`, `model_dump` or reading camel-case fields
   (`sessionId`, `toolName`) on SDK objects: they are dataclasses with snake-case fields.
6. Read `RunResult.events` instead of filtering `RunResult.notifications`; subscribe with
   `on_event`.
7. Catch `RpcError` and compare its `reason`, not message text.
8. Replace JavaScript plugin bundles added with `dsh plugin add` by a plugin process
   or an MCP server ([DH-ADR-4](../design.md#dh-adr-4)), installed from a local
   directory the operator places ([DH-ADR-13](../design.md#dh-adr-13)); nothing is
   downloaded. A tool defined in Python is a third way only if the owner accepts that
   new scope ([DH-ADR-PYSDK-8](#dh-adr-pysdk-8)).
9. Remove calls to `deepseek_harness.office`, `download_office` and
   `download_primary_runtime` ([DH-ADR-PYSDK-7](#dh-adr-pysdk-7)).
10. Turn on anything that used to be on by default and sent data off the machine.
    Session-log upload, analytics and telemetry are off until the user opts in
    ([DH-ADR-9](../design.md#dh-adr-9)); a program that relied on upstream's default
    upload gets none.

## 7. Decisions

<a id="dh-adr-pysdk-1"></a>
### DH-ADR-PYSDK-1 The harness is Go; the Python client stays Python, pure and thin

- **Decision.** "Everything in Go" means every part of the harness: the host, the SDK
  protocol server, every tool, the code generator and the release tools. The library a
  Python program imports is still written in Python, with no compiled extension. It is
  kept thin by a rule: no product logic in Python. Anything the host knows, the host
  sends ([§6.2](#62-the-python-api)). A Go client package for Go programs that embed or
  drive the harness is **not** part of this specification; it belongs to area A20, which
  owns the Go message types, the schema and the server. Inference: the harness already
  needs such a client for itself, because one subagent backend runs a task in a fresh
  harness process over this protocol
  ([upstream/wire-and-api.md §5.4](../upstream/wire-and-api.md#54-how-the-sdks-launch-and-talk-to-the-host)).
- **Why.** The owner asked for a Go reimplementation of everything. A Python interpreter
  can only import Python or a C extension, so some Python must exist for a Python user.
  The choice is how much, and the answer is: the part that cannot be anywhere else.
- **Tradeoff.** Alternatives considered. (a) Publish no Python package and document the
  protocol: every user rewrites the launcher, the ladder and the reader, and
  [DH-ADR-1](../design.md#dh-adr-1) puts the Python SDK in scope. (b) Build the host as
  a C shared library and load it into Python: it needs cgo, which the release plan
  avoids ([design CF-5](../design.md#8-conflicts-and-gaps-between-the-foundation-recommendations));
  a host crash would end the user's program; and closing the input would no longer be a
  stop signal, as [DH-ADR-WIRE-6](../upstream/wire-and-api.md#dh-adr-wire-6) records.
  The cost of the chosen option is that a second language remains in the repository,
  with its own tests and release artifact.
- **Serves.** [DH-O-13](../design.md#dh-o-13).
- **Verified by.** `DH-T-PYSDK-5` (the run result comes from the host's notice, not from
  event inspection), `DH-T-PYSDK-9` (no dependency, no compiled file in the pure wheel),
  [DH-E-PYSDK-1](#dh-e-pysdk-1).

<a id="dh-adr-pysdk-2"></a>
### DH-ADR-PYSDK-2 Wire types and method stubs are generated into standard-library dataclasses; `pydantic` is removed

- **Decision.** The Python client has a hand-written part (transport, launcher, facade)
  and a generated part. A Go generator reads the checked-in SDK protocol schema and
  writes one Python module: a frozen dataclass per message type, decode and encode
  functions, one method stub per protocol method, the error-code constants and the
  protocol version. The generated file is checked in. Decoding checks required fields,
  types and closed sets of values and raises `ProtocolError`; a field the client does not
  know is ignored, so the host can add fields without a new protocol version. The
  generator accepts a stated subset of schema features and fails on anything else. The
  payload of a session event is not typed ([§6.2](#62-the-python-api)).
- **Why.** `DH-LIB-PYSDK-R2` and `-R3`. Upstream uses `pydantic` for exactly this
  boundary check ([§2.5](#25-how-the-five-dependencies-are-used)) but writes the models
  by hand. Generation keeps the check and removes both the copy and the dependency.
- **Tradeoff.** We own a generator, and the protocol's Go types must stay inside the
  subset it understands. SDK objects lose the `pydantic` methods some users call. The
  generator is written in Go so that producing the file needs no Python.
- **Serves.** [DH-O-13](../design.md#dh-o-13);
  [DH-ADR-WIRE-6](../upstream/wire-and-api.md#dh-adr-wire-6).
- **Verified by.** `DH-T-PYSDK-7`, `DH-T-PYSDK-8`, `DH-T-PYSDK-9`.

<a id="dh-adr-pysdk-3"></a>
### DH-ADR-PYSDK-3 Host requests go to typed handlers; there is no generic reverse-request queue

- **Decision.** The client is bidirectional. Each kind of host request (approval,
  question, tool call) has one registered handler. The client advertises a capability
  only when its handler exists. Each request runs on its own worker thread with a
  cancellation event that is set when the host withdraws the request, when the client
  closes and when the connection is lost. A late or cancelled answer is not sent. A
  handler error becomes an error reply, which the host treats as a refusal. A host
  request with an unknown method is answered "method not found" by the client itself. A
  frame that has both an id and a method is always a request and can never complete a
  pending call. The number of handler threads is bounded; a request over the bound is
  refused. `next_request`, `respond`, `respond_error` and `notify` are not public.
- **Why.** Approvals are answered by replying to a host request
  ([DH-ADR-WIRE-4](../upstream/wire-and-api.md#dh-adr-wire-4)), so the reverse direction
  must stay. What upstream's proposal objected to was an open-ended reverse API with no
  protocol behind it; typed handlers remove that without removing the feature. One style
  also ends the split in `UP-DEBT-found.L18.4`.
- **Tradeoff.** A caller can no longer answer an arbitrary host request by hand; a new
  kind of request needs a client release. Handlers run on threads, so they must be
  thread-safe.
- **Serves.** [DH-O-13](../design.md#dh-o-13), [DH-O-7](../design.md#dh-o-7) (with nobody
  to ask, the answer is no).
- **Verified by.** `DH-T-PYSDK-1`, `DH-T-PYSDK-4`, [DH-E-PYSDK-1](#dh-e-pysdk-1).

<a id="dh-adr-pysdk-4"></a>
### DH-ADR-PYSDK-4 The Go binary ships inside per-platform wheels of one distribution; nothing is downloaded

- **Decision.** One distribution. Each release publishes a platform wheel per target
  with the binary inside, and one pure wheel as the fallback
  ([§6.4](#64-the-wheel-and-how-the-binary-is-found)). The client finds the binary from
  an explicit path, an environment variable or the installed wheel, and from nowhere
  else. The package never downloads anything: not on import, not on first use, and not
  through an explicit command in the first version.
- **Why.** `DH-LIB-PYSDK-R4`. With the binary in the wheel, the installer's hash check
  and the user's lock file cover it, an offline or read-only machine works, and there is
  no cache to lock, clean or secure. One distribution, where upstream has two, removes
  the exact-version pin and the class of "mismatched pair" errors that upstream's
  installed-wheel check exists to catch
  (`.agents/notes/implemented/testing/2026-08-23-installed-python-wheel-black-box-ci.md:17`).
- **Tradeoff.**

  | Option | Pros | Cons |
  |---|---|---|
  | **Chosen: binary in platform wheels, one distribution** | Offline; covered by lock files; no pin; one name | Every release uploads one wheel per target; total size is the binary times the number of targets; each wheel must stay under the index's limit (`DH-LIB-PYSDK-R8`) |
  | Two distributions, as upstream | The client wheel stays tiny and pure | A pin to maintain and check; two names; two uploads that can disagree |
  | Download on first use, verified against digests in the package | One small wheel | Network on first run; a second place where trust, proxies, mirrors and timeouts must be handled (upstream needs all four for its optional downloads, `python/sdk-runtime/README.md:26`); the binary is outside the user's lock file; needs a writable cache and an atomic publish |
  | An explicit download command | No surprise network use | The same costs as above, deferred to a command; not needed while every release target has a wheel |

  A platform without a wheel is served by `dsh_bin` and a binary from the release
  archive, whose checksum file the user verifies.
- **Serves.** [DH-O-13](../design.md#dh-o-13);
  [DH-ADR-WIRE-6](../upstream/wire-and-api.md#dh-adr-wire-6);
  [DH-ADR-TOOLCHAIN-13](../upstream/toolchain.md#dh-adr-toolchain-13).
- **Verified by.** `DH-T-PYSDK-10`, `DH-T-PYSDK-11`, `DH-T-PYSDK-12`,
  [DH-E-PYSDK-2](#dh-e-pysdk-2).

<a id="dh-adr-pysdk-5"></a>
### DH-ADR-PYSDK-5 Wheels are written by a Go tool in the release job

- **Decision.** A Go tool writes every wheel from the release binaries and the Python
  sources ([§6.4](#64-the-wheel-and-how-the-binary-is-found)). The checks of upstream's
  build hook are kept as checks of this tool: no source distribution, one binary that
  matches the target, an exact file list, a size limit. The output is repeatable: the
  same inputs give the same bytes. The Python tests run with the standard `unittest`
  runner, so neither the build nor the tests install a Python package.
- **Why.** `DH-LIB-PYSDK-R1`, `-R5`, `-R7`, `-R8`. The release builds every target on one
  runner ([DH-ADR-TOOLCHAIN-13](../upstream/toolchain.md#dh-adr-toolchain-13)), so a
  Python build tool could never infer the platform and would only be zipping files. A
  wheel is a zip archive with three metadata files.
- **Tradeoff.** We take on the wheel format's details (hash encoding in `RECORD`, the
  executable bit in the archive, metadata fields). The fallback is `hatchling`
  ([§5](#5-go-choice)). `unittest` is plainer than `pytest`; the Python test suite is
  small enough for that.
- **Serves.** [DH-O-13](../design.md#dh-o-13).
- **Verified by.** `DH-T-PYSDK-10`, `DH-T-PYSDK-11`, [DH-E-PYSDK-2](#dh-e-pysdk-2).

<a id="dh-adr-pysdk-6"></a>
### DH-ADR-PYSDK-6 The Python API is redesigned: the model is kept, the names and types change

- **Decision.**

  | | |
  |---|---|
  | **Kept** | A child process over standard input and output; lazy start and a context manager; an explicit home for the library; `run()` returning the final answer, the finish reason and the events; a session handle; resume by id; one-shot approval outcomes; question callbacks with a cancellation event; a bounded handshake; timeouts that never cancel work; the close ladder; errors that carry the exit code and the standard-error tail; a profile and ordered overlay files; `dsh_bin`; a `dsh` console command; Python 3.10 or newer |
  | **Changed** | Distribution and import names; SDK objects are dataclasses with snake-case fields; approvals are a callback; results and scoping come from the host; events have a typed envelope; errors carry a stable reason code; the handshake checks a protocol version; one distribution; the installed `dsh` command behaves like the ordinary command |
  | **Added** | `cancel()`, `close()` and `history()` on a session, from [DH-ADR-WIRE-5](../upstream/wire-and-api.md#dh-adr-wire-5); `verify_runtime()`; tools defined in Python ([DH-ADR-PYSDK-8](#dh-adr-pysdk-8)) |
  | **Dropped** | The generic request queue; `pydantic` types; Office operations and resource downloads; the Node development carrier; npm plugin bundles |

  The steps for a migrating user are in [§6.6](#66-what-a-migrating-user-must-do).
- **Why.** The protocol under the API changes ([DH-ADR-2](../design.md#dh-adr-2),
  WIRE-5), the type library goes, and the names cannot be reused. Keeping method
  signatures over a different protocol would promise a compatibility that does not hold.
  The mental model is worth keeping because it is sound and users know it.
- **Tradeoff.** Every upstream user edits their code. There is no compatibility shim: it
  would have to imitate `pydantic` objects and the old notification stream.
- **Serves.** [DH-O-13](../design.md#dh-o-13).
- **Verified by.** `DH-T-PYSDK-2`, `DH-T-PYSDK-3`, `DH-T-PYSDK-5`, `DH-T-PYSDK-6`,
  [DH-E-PYSDK-1](#dh-e-pysdk-1).

<a id="dh-adr-pysdk-7"></a>
### DH-ADR-PYSDK-7 Office operations and resource downloads leave the Python package

- **Decision.** The Python package has no `office` module, no `download_office` and no
  `download_primary_runtime`. This is a recorded exception to
  [DH-ADR-1](../design.md#dh-adr-1) for the Python package only: the capability itself
  is specified by the office library and area documents
  ([deepseek-ai-libreoffice-kit.md](deepseek-ai-libreoffice-kit.md), area A16). If that
  area exposes document conversion as a `dsh` command, a Python user calls it with
  `subprocess`; this specification adds no wrapper.
- **Why.** These functions are not a client of the SDK protocol: they start no agent and
  no session (`python/sdk/README.md:13`). They exist in the Python package because the
  engine is a Node tool that needs its own Node runtime, a download and a cache
  (`python/sdk-runtime/README.md:24-28`). The second download carries Node and pnpm for
  managing npm plugins, which the Go design does not have
  ([DH-ADR-4](../design.md#dh-adr-4)). `Pillow` is needed only to test the image output
  ([§2.5](#25-how-the-five-dependencies-are-used)).
- **Tradeoff.** A Python user loses three convenience functions with typed results. The
  check that a rendered page has visible content is still needed; it belongs with the
  office area's tests (open question 7).
- **Serves.** [DH-O-13](../design.md#dh-o-13) (a smaller, protocol-only client).
- **Verified by.** `DH-T-PYSDK-9` (the wheel's file list and metadata).

<a id="dh-adr-pysdk-8"></a>
### DH-ADR-PYSDK-8 A tool defined in Python is a host-registered tool answered over the same connection

- **Decision.** New scope, priority P2, to build only if the owner accepts it (open
  question 2). The caller passes Python functions with a name, a description and a
  parameter schema. The client declares them in the handshake. The host registers each
  as a tool in the scope of the sessions that client creates, so the model sees them
  like any other tool. When the model calls one, the call goes through the host's
  ordinary guarded pipeline (schema check, policy, approval, result limits) and the tool
  body is a host request to the client, which runs the function on a worker thread and
  replies with the result. Cancellation and connection loss follow
  [DH-ADR-PYSDK-3](#dh-adr-pysdk-3); a lost connection gives the tool result "outcome
  unknown". The wire method and its fields belong to area A20.
- **Why.** Upstream has no way to give the model a Python function
  ([§2.2](#22-the-python-api-surface)); its answer is a JavaScript plugin, which the Go
  design does not load. The two existing Go routes, an MCP server and a plugin process,
  both run the tool in another process, so it cannot use the calling program's objects.
  The reverse channel needed for approvals already carries everything this requires.
- **Tradeoff.** The function runs in the caller's process with the caller's rights,
  outside the sandbox. That is acceptable because the calling program started the host
  and is its owner, but it must be said: the pipeline's checks run before the call is
  sent, and nothing confines the function itself. The tools vanish when the client
  disconnects.
- **Serves.** [DH-O-13](../design.md#dh-o-13), [DH-O-6](../design.md#dh-o-6).
- **Verified by.** `DH-T-PYSDK-14`, [DH-E-PYSDK-4](#dh-e-pysdk-4).

<a id="dh-d-pysdk-1"></a>
### DH-D-PYSDK-1 A pure-Python client that starts, drives and stops the harness

- **Result and why it matters.** A Python program can create or resume a session, send
  input, receive events, answer approvals and questions, cancel, read history and shut
  down, with typed errors, and without leaving a process behind. This is the Python part
  of [DH-O-13](../design.md#dh-o-13).
- **How it is implemented.** Three layers ([§6.1](#61-shape)). The transport starts the
  child and runs a reader thread that routes each line to a response waiter, a handler
  thread or a bounded event buffer, and a second thread that keeps a bounded tail of
  standard error. The facade (`Harness`, `Session`) is a thin sequence of generated
  method calls: `run()` subscribes, sends, and returns when the host's completion notice
  for its message arrives. The close ladder and the handshake follow
  [§6.3](#63-launch-and-handshake) and [§6.5](#65-ownership-failure-retry-rollback-and-cleanup).
  Four examples (minimal run, approval, question, resume after restart) are kept
  runnable by tests, as upstream keeps its examples.
- **Components and files.** The hand-written Python modules under the client directory;
  fake-peer scripts for tests.
- **Depends on.** Implementation: [DH-D-PYSDK-2](#dh-d-pysdk-2). From other areas: the
  method set, the completion notice for prompts and commands, the root session id on
  notifications and the bounded exit after end-of-file (A20;
  [§4.3](#43-the-two-wire-decisions-measured-against-the-real-sdk)); the launch form and
  home selection (A24). Runtime prerequisites: Python 3.10 or newer and a `dsh` binary.
- **Outcome.** [DH-O-13](../design.md#dh-o-13).
- **Priority.** P1.
- **Done when.** `DH-T-PYSDK-1` to `DH-T-PYSDK-6` pass, and
  [DH-E-PYSDK-1](#dh-e-pysdk-1) and [DH-E-PYSDK-3](#dh-e-pysdk-3) pass on Linux, macOS
  and Windows.

<a id="dh-d-pysdk-2"></a>
### DH-D-PYSDK-2 Python wire types and method stubs generated from the protocol schema

- **Result and why it matters.** A change to a protocol message in Go reaches Python by
  running one command, and a forgotten run fails a test. The hand-kept copy of
  `UP-DEBT-found.L18.2` cannot come back.
- **How it is implemented.** A Go generator reads the schema file that area A20 checks in
  and renders one Python module from templates
  ([DH-ADR-PYSDK-2](#dh-adr-pysdk-2)). A Go test regenerates in memory and compares with
  the checked-in file. A second Go test writes sample messages from real Go values to a
  folder of JSON files; a Python test decodes and re-encodes each and compares, so the
  two languages are held to the same bytes and not only the same shapes.
- **Components and files.** The generator package, its templates, the generated Python
  module, the sample folder.
- **Depends on.** From area A20: the schema, including a method table. No runtime
  prerequisite beyond the Go toolchain.
- **Outcome.** [DH-O-13](../design.md#dh-o-13).
- **Priority.** P1.
- **Done when.** `DH-T-PYSDK-7`, `DH-T-PYSDK-8` and `DH-T-PYSDK-9` pass, and
  [DH-E-PYSDK-1](#dh-e-pysdk-1) passes against the real host using the generated module.

<a id="dh-d-pysdk-3"></a>
### DH-D-PYSDK-3 Platform wheels that carry the Go binary, written by a Go tool

- **Result and why it matters.** `pip install` on a supported machine yields a working
  harness with no other runtime, no download and no build step
  (`DH-LIB-PYSDK-R4`). It replaces the pipeline of `UP-DEBT-found.L18.1`.
- **How it is implemented.** The wheel writer of
  [§6.4](#64-the-wheel-and-how-the-binary-is-found) runs in the release job after the
  binaries are built, once per row of a target table (target, platform tags, binary
  name) and once for the pure wheel. It reads each binary's file header to confirm the
  operating system and CPU, and on macOS the minimum system version the binary declares,
  and refuses a tag that promises more than the binary supports. It writes the
  manifest, the metadata and `RECORD`, then checks its own output by reading it back.
  The release job compares each embedded binary's hash with the release checksum file.
- **Components and files.** The wheel writer package, the target table, the release
  workflow step.
- **Depends on.** The release binaries of
  [DH-D-TOOLCHAIN-5](../upstream/toolchain.md#dh-d-toolchain-5) (decision
  [DH-ADR-TOOLCHAIN-13](../upstream/toolchain.md#dh-adr-toolchain-13)); the Python sources
  of [DH-D-PYSDK-1](#dh-d-pysdk-1) and [DH-D-PYSDK-2](#dh-d-pysdk-2) for a publishable
  wheel (the tool itself can be built and tested with placeholder sources). Publishing
  additionally needs an index account and the final names (open question 1).
- **Outcome.** [DH-O-13](../design.md#dh-o-13).
- **Priority.** P1.
- **Done when.** `DH-T-PYSDK-9`, `DH-T-PYSDK-10` and `DH-T-PYSDK-11` pass,
  [DH-E-PYSDK-2](#dh-e-pysdk-2) passes on every target, and
  [DH-E-PYSDK-1](#dh-e-pysdk-1) passes with wheels this tool wrote.

<a id="dh-d-pysdk-4"></a>
### DH-D-PYSDK-4 The installed binary is found, checked and runnable as `dsh`

- **Result and why it matters.** The client starts the binary that was installed with
  it, says clearly when there is none or it is damaged, and gives an operator a way to
  prove the file is the released one. Typing `dsh` in the environment runs the same
  binary.
- **How it is implemented.** A resolver with the fixed order of
  [§6.3](#63-launch-and-handshake), step 1; the cheap start checks and the on-demand
  `verify_runtime()` of [§6.4](#64-the-wheel-and-how-the-binary-is-found); the console
  shim. The handshake's build-version check completes the identity proof.
- **Components and files.** The launcher module and the console entry of the Python
  package.
- **Depends on.** Implementation: [DH-D-PYSDK-3](#dh-d-pysdk-3) (the manifest format).
- **Outcome.** [DH-O-13](../design.md#dh-o-13).
- **Priority.** P1.
- **Done when.** `DH-T-PYSDK-6`, `DH-T-PYSDK-12` and `DH-T-PYSDK-13` pass, and
  [DH-E-PYSDK-2](#dh-e-pysdk-2) and [DH-E-PYSDK-1](#dh-e-pysdk-1) (whose step 2 is the
  identity check) pass.

<a id="dh-d-pysdk-5"></a>
### DH-D-PYSDK-5 A Python function can be offered to the model as a tool

- **Result and why it matters.** An embedding program gives the agent access to its own
  data and functions without writing a separate server. Upstream cannot do this.
- **How it is implemented.** [DH-ADR-PYSDK-8](#dh-adr-pysdk-8): declaration in the
  handshake, a handler kind in the dispatcher of
  [DH-ADR-PYSDK-3](#dh-adr-pysdk-3), and result encoding through the generated types.
  The host side (registering the tools in the session scope and sending the call) is
  area A20's and the tool pipeline's.
- **Components and files.** A tool-registration module in the Python package; additions
  to the generated module.
- **Depends on.** Implementation: [DH-D-PYSDK-1](#dh-d-pysdk-1),
  [DH-D-PYSDK-2](#dh-d-pysdk-2). From area A20: the method and its host side. The
  owner's acceptance of the new scope.
- **Outcome.** [DH-O-13](../design.md#dh-o-13).
- **Priority.** P2.
- **Done when.** `DH-T-PYSDK-14` passes and [DH-E-PYSDK-4](#dh-e-pysdk-4) passes.

### 9.2 Real-environment scenarios

This product has no remote lab ([design §3.4](../design.md#34-how-outcomes-are-proven)).
A real environment here is a real operating system, a real package installer and, where
stated, a real model API. Every scenario runs from a directory outside the repository
with `PYTHONPATH` unset. Each run records: the commit and version, each wheel's file name
and SHA-256, the operating system and Python version, the commands, the session ids and
the result. A scenario that is missing, skipped, blocked or failed is open, not passed.
Passing proves the stated behaviour for the tested build, platforms and inputs only.

<a id="dh-e-pysdk-1"></a>
#### DH-E-PYSDK-1 An installed wheel drives a real model through approval, cancel, restart and resume

- **Proves.** [DH-D-PYSDK-1](#dh-d-pysdk-1), [DH-D-PYSDK-2](#dh-d-pysdk-2),
  [DH-D-PYSDK-3](#dh-d-pysdk-3), [DH-D-PYSDK-4](#dh-d-pysdk-4). It is the
  [DH-ADR-WIRE-5](../upstream/wire-and-api.md#dh-adr-wire-5) scenario driven from Python,
  as [DH-ADR-WIRE-6](../upstream/wire-and-api.md#dh-adr-wire-6) asks.
- **Given.** One runner each for Linux, macOS and Windows. The wheel files from the
  release build of the commit under test, in a local folder. A new virtual environment on
  the oldest supported Python, outside the checkout. A real model API key supplied at run
  time through the environment of a trusted workflow, never on a pull request from a
  fork; a missing key fails the run. A new temporary directory as home and another as
  workspace.
- **When.** All steps run on the runner. (1) Install the wheel from the local folder with
  no index access. (2) Identity check: the package was imported from the environment and
  not from a checkout; `runtime_path()` is inside the installed package;
  `verify_runtime()` passes; the handshake's build version equals the wheel's version.
  (3) With an approval handler that allows once, ask the model to create a file with
  given content through its shell tool. (4) In the same session, start a long-running
  task and call `cancel()`. (5) Call `close()`. (6) Start a new `Harness` on the same
  home, `resume()` the session, read `history()`, and ask the model to read the file
  back.
- **Then.** Step 2 passes before any prompt is sent. Step 3: the handler was called at
  least once, the file exists with the exact content, and the finish reason is
  "completed". Step 4: the run ends with a cancelled reason within a stated bound. Step
  5: no `dsh` process and no child of it remains. Step 6: history contains every event
  seen in steps 3 and 4, once and in order; the second answer contains the file's
  content.
- **Cleanup.** Remove the virtual environment, the home and the workspace. If a process
  remains or removal fails, keep the home, the standard-error tail and the process list
  as evidence and fail the run.

<a id="dh-e-pysdk-2"></a>
#### DH-E-PYSDK-2 On every target a real installer selects a wheel whose binary runs and verifies

- **Proves.** [DH-D-PYSDK-3](#dh-d-pysdk-3), [DH-D-PYSDK-4](#dh-d-pysdk-4),
  `DH-LIB-PYSDK-R4`.
- **Given.** One real machine or container per row of the target table, including a
  musl-based Linux and Windows on arm64, plus one platform with no wheel. All wheels of
  one release build served from a local folder as a flat index. Two installers: `pip`
  and `uv`. No model key is needed.
- **When.** On each machine, for each installer and for the oldest and newest supported
  Python: (1) create a new environment and install the distribution by name from the
  local index; (2) record which wheel file was chosen; (3) run `dsh --version` through
  the console command; (4) call `verify_runtime()`; (5) start a `Harness` with a
  temporary home, complete the handshake and close; (6) flip one byte of the installed
  binary and call `verify_runtime()` again.
- **Then.** The chosen wheel is the one the target table names. The printed version
  equals the wheel version. Step 4 passes and step 6 fails naming the file. The binary's
  hash equals the entry for that target in the release checksum file. On the platform
  with no wheel, the pure wheel is installed and step 5 raises `RuntimeNotFoundError`
  naming `dsh_bin`.
- **Cleanup.** Remove the environments and temporary homes. Keep the installer logs of
  any failing combination.

<a id="dh-e-pysdk-3"></a>
#### DH-E-PYSDK-3 A killed host and a killed client leave no orphan and an honest session

- **Proves.** [DH-D-PYSDK-1](#dh-d-pysdk-1).
- **Given.** The environment of [DH-E-PYSDK-1](#dh-e-pysdk-1) on Linux, macOS and
  Windows, with a real model key and a session that is running a shell command which
  sleeps.
- **When.** Case A: from outside, kill the `dsh` process while `run()` is waiting. Case
  B, in a fresh session: kill the Python process while the host is running the command.
  After each case, start a new client on the same home and `resume()` the session.
- **Then.** Case A: `run()` raises `TransportClosedError` with the exit status and the
  standard-error tail; pending handlers see their cancellation event; a further call
  fails the same way until `close()`. Case B: the host process and every process it
  started end within the stated bound. In both cases, after resume, the interrupted turn
  is closed as interrupted and the unfinished tool call is reported as not started or
  outcome unknown; nothing is replayed.
- **Cleanup.** Kill any process left from the test's process tree, then remove the
  temporary directories. A surviving process is a failure; keep its command line and the
  home.

<a id="dh-e-pysdk-4"></a>
#### DH-E-PYSDK-4 A real model calls a tool defined in Python

- **Proves.** [DH-D-PYSDK-5](#dh-d-pysdk-5).
- **Given.** The environment of [DH-E-PYSDK-1](#dh-e-pysdk-1). A Python function
  registered as a tool that returns a random value created by the test and never written
  to disk, and an approval handler.
- **When.** (1) Ask the model to call the tool and repeat its result. (2) Ask again with
  a handler that rejects. (3) Ask again and close the client while the function is
  blocked.

## 10. Risks and open questions

1. **Names (owner).** The distribution name, the import name and whether the index
   account uses trusted publishing with public attestations. Upstream switches
   attestations off to hide a private repository (`python/development.md:106`); this
   project may have no such reason. Whether the chosen names are free on the package
   index was not checked.
2. **Tools defined in Python (owner, then A20).** [DH-ADR-PYSDK-8](#dh-adr-pysdk-8) is new
   scope. If it is not accepted, the answer for a Python user is an MCP server or a
   plugin process, and [DH-D-PYSDK-5](#dh-d-pysdk-5) is not built.
3. **Platform tags and binary size (needs a real build).** The exact `manylinux` and
   `musllinux` tags a static Go binary may claim, the macOS minimum of the release
   toolchain, and the size of `dsh`. None can be learned without building. If the binary
   exceeds the index's per-file limit, the choices are a raised limit on request,
   stripping, or the download option of [DH-ADR-PYSDK-4](#dh-adr-pysdk-4).
4. **Acceptance of hand-written wheels (needs a real upload).** Whether the package index
   and both installers accept the wheel writer's output can only be shown by
   [DH-E-PYSDK-2](#dh-e-pysdk-2) and a test upload. The fallback is in
   [§5](#5-go-choice).
5. **Requests to area A20** ([§4.3](#43-the-two-wire-decisions-measured-against-the-real-sdk),
   items 1 to 5): a completion notice for commands as well as prompts; the root session
   id on scoped notifications; the full method set, including command input, resume with
   a permission preset and the working-directory methods; a method table in the schema;
   a bounded host exit after end-of-file; and the numbers this document leaves unset
   (frame size, close budgets, buffer sizes).
6. **Answered by area A24.** The binary does not refuse the default home when started as
   an SDK server; home selection is the launcher's, and a client passes `--home`. The
   Python client keeps its own rule of step 2 in [§6.3](#63-launch-and-handshake): it
   never starts a child without an explicit home.
7. **Request to area A16.** The check that a rendered Office page has visible, correctly
   ordered content (`scripts/fixtures/office-render.py:55-78`) needs a home in Go;
   inference: the standard `image/png` decoder is enough for it.
8. **An asyncio interface.** Upstream is synchronous. An asynchronous facade over the
   same transport is not designed here.
9. **Risk: the Python suite is much smaller than upstream's.** Upstream has about 296
   kilobytes of Python tests, most of them exercising product behaviour through the SDK.
   The Go design tests that behaviour in Go. If the Go protocol tests are thin, the
   Python client will find the gaps late.
10. **Risk: a second language in the release.** A Python-only defect needs a full
    release, because the client and the binary share one version.

## 1. What it is and why upstream needs it

A **schema** is a machine-readable description of what a piece of data must look like:
which fields exist, their types, which are required, and what values are allowed.
**Validation** is checking a value against a schema. The harness needs both because most
of its data crosses a boundary where the compiler cannot help: a human writes plugin
configuration in a YAML file, a language model writes tool arguments as JSON text, another
process sends a message, and a session file written last month is read back today.

zod is a TypeScript library in which a developer writes a schema as code
(`z.object({ id: z.string() })`) and gets both a runtime checker and a compile-time type.
Upstream uses it for process-to-process messages, saved state and records read back from
disk. It is only one of **five** schema systems upstream runs side by side. **JSON Schema**
is the standard JSON format for schemas; it is what a model provider accepts as the
description of a tool's arguments. A **type graph** is a data structure listing every
type a program declares and how they refer to each other. A **fingerprint** is a hash of a
type's shape, used to notice that a saved format changed.

## 5. Go choice

<a id="dh-adr-schema-1"></a>
### DH-ADR-SCHEMA-1 The Go type is the only declaration of a data shape

- **Decision.** A shape is a Go struct (or defined type) with `json` tags. Everything else
  is derived from it by reflection through one harness package, `schema`: the JSON Schema
  document, the validator, the settings form, the catalog page and the fingerprint. Field
  facts that Go types cannot carry go in struct tags: the description in the
  `jsonschema` tag, and constraints and hints in a `dsh` tag (section 6).
- **Why.** Go keeps type information at run time, TypeScript erases it. Upstream needs a
  second declaration because its types vanish before the program runs; Go does not.
- **Tradeoff.** Go comments are not visible to reflection, so a description must be
  written in a tag, not a doc comment; a test fails when one is missing. Struct tags are
  strings the compiler does not check, so the same test parses every tag.
- **Serves.** `DH-LIB-ZOD-R1`, `R2`, `R7`, `R8`; removes `UP-DEBT-found.F3.1` to `F3.3`.
- **Verified by.** `DH-T-ZOD-1`, `DH-T-ZOD-2`.

<a id="dh-adr-schema-2"></a>
### DH-ADR-SCHEMA-2 JSON Schema is the one derived form, handled by one module

- **Decision.** JSON Schema (draft 2020-12) is the only form a shape is converted into.
  One module, `github.com/google/jsonschema-go`, infers it from Go types, validates values
  against it and checks defaults. Only the `schema` package imports that module.
  Schemas sent to a model must stay inside a fixed keyword subset, checked at registration.
- **Why.** The model provider, MCP (Model Context Protocol) servers, external plugins and
  editors all speak JSON Schema, so it is needed in any case. Using the same document to
  describe a tool to the model and to check what the model sends back means the two cannot
  drift apart.
- **Tradeoff.** The module is version 0.x, so its API may change; the single import point
  bounds the cost. Its patterns use Go's regular-expression syntax, not JavaScript's.
- **Serves.** `DH-LIB-ZOD-R2` to `R6`, `R11`, `R12`; removes `UP-DEBT-found.F3.4`.
- **Verified by.** `DH-T-ZOD-3` to `DH-T-ZOD-6`, `DH-T-ZOD-10`.

<a id="dh-adr-schema-3"></a>
### DH-ADR-SCHEMA-3 Defaults are a Go value; input is decoded on top of it

- **Decision.** A component states its defaults as a function returning its config type,
  which the cordis port already supports (`cordis.WithDefaults`,
  `src/go/cordis/component.go:73`). JSON input is decoded onto that value, so absent
  fields keep their defaults. The `default` annotations in the derived schema are
  produced by serialising the same value. For config, a field is required only when
  tagged `dsh:"required"`; for messages, tool input and records, a field is required
  unless its `json` tag says `omitempty` or `omitzero`.
- **Why.** Upstream writes 716 defaults inside schemas; a default that is also a Go value
  is checked by the compiler and cannot disagree with the type.
- **Tradeoff.** Two rules for "required". They match how each kind is decoded: config onto
  defaults, where absence is normal, and messages onto an empty value, where it is not.
- **Serves.** `DH-LIB-ZOD-R6`.
- **Verified by.** `DH-T-ZOD-6`.

<a id="dh-adr-schema-4"></a>
### DH-ADR-SCHEMA-4 Reflection at startup replaces build-time type-graph generation

- **Decision.** Nothing is generated at build time. A remote method, tool or event type is
  registered with its Go types, and its schema is derived when it is registered.
  Fingerprints of persisted types are a hash of a canonical form of the derived schema,
  compared by a test against a committed inventory file.
- **Why.** The typert generator, the persistence extractor and their source maps exist to
  recover types the TypeScript compiler erased. See [typescript.md](typescript.md).
- **Tradeoff.** No generated typed client for other languages; they get JSON Schema files
  (`DH-LIB-ZOD-R11`). A type reflection cannot describe (a recursive type, an interface
  field) needs an explicit registration, and fails loudly without one.
- **Serves.** `DH-LIB-ZOD-R9`, `R10`, `R11`.
- **Verified by.** `DH-T-ZOD-2`, `DH-T-ZOD-8`, `DH-T-ZOD-9`.

## 6. Design notes

**Package.** `schema`, in the harness module at `src/harness/internal/schema`: every
implementation package sits under `internal/` ([../design.md](../design.md) §4.2), and
area A23 owns it ([../areas/util-test-support.md](../areas/util-test-support.md),
`DH-D-UTIL-1`). It
imports the standard library and the chosen module only, and does not import cordis, so
every other harness package may use it. Shape of the API (illustrative, not final):

```go
t, err := schema.Of[BashInput]()        // derive once per Go type; cached; immutable
t.JSONSchema()                          // the document, for the model, catalog, UI, export
issues := t.Decode(raw, &in)            // structural check, strict decode, then in.Validate()
t.Fingerprint()                         // hash of the canonical wire shape
schema.FromJSON(doc)                    // a schema supplied at run time by an external plugin
schema.Union[Frame]("type", variants)   // one-of-several shapes told apart by one field
```

**Struct tags.** `json` gives the wire name and, outside config, optionality.
`jsonschema:"..."` is the description (the module's own tag). `dsh:"..."` is a
comma-separated list: `min=`, `max=`, `enum=a|b`, `pattern=`, `required`, and the metadata
words `live` and `secret` and `ui=` explained in [schemastery.md](schemastery.md).
Metadata is written into the document as `x-dsh-*` keywords, which validators ignore.

**How each job is done.**

| Job (section 1) | Go mechanism |
|---|---|
| 1 Config | `cordis.WithDefaults` plus a `cordis.Schema` built by `schema` that checks tag constraints and then calls `Validate()`. Detail in [schemastery.md](schemastery.md). |
| 2 Config UI and catalog | The settings page (HTML rendered by the host, DH-ADR-3) and a catalog command both walk `t.JSONSchema()`. No source parsing. |
| 3 Tool schema for the model | A tool is registered with its input type; the document is derived then. A tool may edit the derived document before registering (an enum that depends on config, `docs/tool-catalog.md:8`); the edited document is also the one used for checking. |
| 4 Tool arguments | `t.Decode`. On any issue the tool body is not called and the issues are returned to the model as a tool error. |
| 5 Wire messages | `t.Decode` at the boundary, for the plugin protocol and the SSH helper. |
| 6 Persisted data | `t.Decode` on read; `t.Fingerprint()` and a committed inventory on change. |
| 7 Remote calls | Methods registered with Go types; schemas by reflection. See [typescript.md](typescript.md). |

**Upstream decisions judged.**

| Upstream decision | Verdict | Reason |
|---|---|---|
| Tool schemas limited to an enforced subset; unsupported keywords are rejected, not ignored (`packages/core/tools/src/json-schema.ts:8`) | keep | A keyword the harness does not enforce would promise the model a rule nobody checks. |
| All violations reported, not only the first (`packages/core/tools/src/json-schema.ts:62`) | keep | The model can fix every mistake in one retry. |
| Tool parameter root accepts unknown keys (`packages/core/tools/src/schema.ts:98`) | change: closed by default, open per tool on request | A misspelt argument is reported to the model instead of being dropped silently. |
| Optional arguments that do not affect the requested operation are accepted, not rejected (`.agents/notes/implemented/bug-fix/2026-09-20-unambiguous-tool-arguments.md`) | keep | `DH-LIB-ZOD-R13`. The rule is model-facing and holds for every provider. It does not weaken the row above: an unknown key is still reported, and a value that is used is still validated. |
| An MCP tool's output schema that is outside the subset falls back to "any JSON" (`packages/mcp/mcp-client/src/tools.ts:299`) | keep | An external server's schema must not be able to break tool loading. |
| Runtime schemas generated from types at build time (typert) | change | DH-ADR-SCHEMA-4. |
| Persisted-type fingerprints with a committed inventory (`docs/persistence-schema.json:1`) | keep the check, change the mechanism | The review process is owned by the session persistence area. |
| `transform` used to brand ids | change | A defined Go type with its own decoding (`DH-LIB-ZOD-R8`). |

**Failure, retry and cleanup.** Deriving a schema has no side effects. If it fails (an
unsupported field type, a cyclic type without an explicit registration, a malformed tag, a
default that breaks a constraint) the component or tool fails to register and the error
names the Go type and field. `DH-T-ZOD-2` derives every registered type, so this failure
is found by the test suite and not at a user's first run. A failed `Decode` leaves
the target value unspecified; callers must discard it. Nothing is retried: the same input
fails the same way.

**Ownership.** A schema derived from a Go type is immutable and cached for the life of the
process, keyed by the type. It holds no file, socket or process, and compiled-in types
cannot be unloaded (DH-ADR-4), so no fiber owns it and nothing needs releasing. A schema
received at run time from an external plugin or MCP server belongs to that plugin's
registration, which the fiber owning the plugin process holds; it is dropped when that
fiber unloads. Any caller may read a schema (access); only the owner replaces it.

## 7. Risks and open questions

- **Violations may not all be reported.** `Resolved.Validate` returns one error value; it
  was not verified that it collects every violation. If it does not, `DH-LIB-ZOD-R4` needs
  the subset validator to be own code (the subset is small). To settle before building.
- **Regular-expression dialect.** Patterns are checked with Go's `regexp`, which has no
  look-ahead or back-references. Harness-authored patterns are written for it. A schema
  from an external MCP server with a JavaScript-only pattern cannot be compiled; the
  design treats that tool's schema as "not checked locally" and still forwards it.
- **Large integers.** Decoding JSON into untyped values turns numbers into 64-bit floats,
  which lose precision above 2^53. Whether the module validates `json.Number` is unchecked.
- **Recursive types** need an explicit schema with `$ref`, because `For` rejects cycles.
- **Settled, cordis port.** `decodeConfig` (`src/go/cordis/component.go:182`) ignores
  unknown config keys, and a `cordis.Schema` sees only the decoded value, so a misspelt
  key cannot be reported from inside the schema. The port gains strict decoding as a
  tree option ([DH-D-CORDIS-8](cordis.md#dh-d-cordis-8)), and the harness creates its
  tree with it.
- **For the tool owners (areas A08, A12, A13).** `DH-LIB-ZOD-R13` gives the general rule.
  Which optional string fields treat an empty value as absent is each tool's own
  declaration: upstream's cases are `grep`'s `include`, the model fields of `subagent`,
  the unused fields of `update_goal` and a blank `justification` on `write` and `edit`
  when no wider sandbox is requested.
- **Open, LLM area.** Each provider accepts a slightly different JSON Schema subset. The
  subset in `DH-LIB-ZOD-R3` must be the intersection for the providers the design supports.
  Proving that a real provider accepts the derived documents is a real-environment
  scenario that belongs to that area; it is not covered by the local tests below.
- **Open, UI area.** Descriptions in tags are in one language. Localised labels need a
  message catalogue keyed by field path.
- **Open, typert and session areas.** They own the remote-call registry and the
  persistence review process; this spec supplies only the primitives they build on.
